# Learn

Vault root: `/Users/nlekanetamba/Documents/DigitalBrain`. Ad hoc, mid-work teaching: just enough understanding to clear whatever's actually blocking the task in front of you right now, not a curriculum module. Deliberately lighter and faster than `/new-session` — for deliberate, sequenced study of the vivenu-core checkout or web3 curricula, use `/new-session` instead. `/learn` reconciles against the same knowledge graph those curricula maintain (`Vivenu/Onboarding/`, `Vivenu/Onboarding-Web3/`) but never writes anything a real curriculum session owns.

**Boundary, stated once:** like the onboarding curricula, `/learn` reads `vivenu-core` (or any other repo) read-only for source material and never edits, commits, or runs anything in it. All of `/learn`'s own writes land only inside this vault, and only in Step 7 — never earlier. **One narrow exception (see Step 8):** when the user takes an *owed work-lesson* surfaced from `Work/Owed-Learning.md`, `/learn` may — only then, and only for that — remove that lesson's row from `Work/Owed-Learning.md` and set `lesson: done` on its `source_session` note. Nothing else under `Work/` ever becomes writable.

## Steps

1. **Anchor to the actual blocker.** Get a one-sentence statement of the task this is meant to unblock. If the current conversation already contains enough context to make it obvious without asking — an error message, a file/line reference, code just discussed — that already satisfies this; only ask explicitly when the topic alone genuinely doesn't imply a task. If asked and still not given, proceed with teaching anyway, but skip Step 7 entirely for this invocation — an anchor-less session never persists, since Step 6's recurrence judgment needs a task to weigh against.

2. **Classify against the knowledge graph — decision only, no writes yet.** Search `Concepts/*.md` and `Modules/*.md` across every track listed in `Vivenu/Track-State.md`'s Tracks table (currently `Vivenu/Onboarding/` and `Vivenu/Onboarding-Web3/`), and `Learning/*.md`, for prior coverage. A topic may match more than one of these — determine every branch that applies; you act on all of them together in Step 7, not here:
   - **A. An existing Concept note covers it, fully or partially.** Plan: don't re-derive it, teach only the delta the current task needs, link back to it.
   - **B. Falls inside an unstarted/partial Module.** Plan: teach only the slice relevant to the blocker.
   - **C. New, recurring-worthy, and in-scope for an existing track** — using the vault's existing bar, "would a future lesson plausibly link to this again?" Plan: this becomes a real, permanent Concepts/ note.
   - **D. Outside any tracked domain entirely.** Plan: this becomes (or updates) a freestanding `Learning/` note.

   A and C can combine: if A's existing note only partially covers the topic — meaning it doesn't already state the specific fact or relationship being taught right now, even in passing — and the uncovered remainder independently clears C's recurrence bar, the plan is to *extend* that same existing note rather than create a new one — never both. B and C can also combine as two independent, compatible actions (see Step 7). If a match under A or C is also covered, even loosely, by an existing `Learning/` note, mention that note and flag it as a merge candidate for a later `/dream` pass — don't merge it yourself. If the topic could plausibly belong to either track, check `Vivenu/Track-State.md`'s `current-track` as a hint before asking; if it's still ambiguous, or the topic genuinely doesn't cleanly fit A/B/C, ask a one-line disambiguating question rather than silently guessing — a wrong guess here creates a permanent, hard-to-find duplicate. If the vault root, a track folder, or a target note can't be found or read, say so and stop rather than guessing or silently skipping ahead.

3. **Scope the minimal prerequisite chain.** Decompose the same way `/explain-first-principles` does, but the floor is different: stop decomposing a given prerequisite once it's either visibly already known to the user, or not load-bearing for the immediate next action — not "ordinary-adult understanding." State the boundary explicitly. If a surfaced prerequisite already has a Concept or Module note, link back to it — lookup only. Never trigger Branch C's or Branch D's note-creation for a prerequisite; both are reserved for the top-level topic itself, so a single invocation can't fan out into several new permanent notes. If the chain turns out to require most of an unstarted Module's worth of material, stop and suggest `/new-session` instead of continuing — don't try to teach the whole module ad hoc.

4. **Teach tight.** Worked-example-first for procedural questions, analogy-build for conceptual ones, scaled to depth — a shallow question gets a couple of sentences, no ceremony. No dedicated Hat persona for this command; this step's own style is the persona. Teach under the **[Teaching Standard (`Teaching-Standard.md`): plain + first-principles, every load-bearing claim derived not asserted (TS-1); cite any file/snippet by `repo/path` (TS-2); corrective hints plain, never cryptic (TS-4)]**.

5. **Confirm by application — this gates everything after it.** Have the user apply the new understanding directly to their actual code/problem; this is the retrieval check. **If that application has the user editing a real, source-controlled file, TS-3 and TS-5 fire (say so in one line): lead any walkthrough step with the why-here (TS-3), and the user writes the production change themselves — you don't (TS-5). If the application is only reasoning or pseudo-code, TS-3/TS-5 don't apply.** Corrective feedback follows TS-4 (plain, never cryptic). If the attempt is wrong, don't proceed to Step 6 or 7 — give corrective feedback, let them retry, and only move on once it actually succeeds. If the user explicitly opts out without confirming, skip Step 6 and 7 entirely for this invocation — nothing gets written anywhere, regardless of branch — and say so plainly. If the user goes silent, changes the subject, keeps giving partial/incomplete answers without ever fully succeeding, or otherwise disengages without an explicit opt-out or a successful application, treat it the same as an explicit opt-out — skip Step 6 and 7, and don't keep prompting for a retry that isn't coming.

6. **Decide whether this is worth persisting.** Only relevant if Step 5 succeeded and Step 1 had a real anchor. Skip persistence for trivial one-offs even then. Branches B and C are usually worth persisting by construction (a Module touch, a recurring Concept); Branch D is where this judgment call matters most.

7. **Persist — the only step that writes anything, and only after Steps 5-6 clear.** Re-read the target file fresh immediately before writing, and apply the smallest possible targeted patch to only the relevant line/section — never reconstruct and rewrite the rest of the file from an earlier read. By branch (apply all that were determined in Step 2):
   - **A (extend case):** update the existing Concept note's body with the delta; never touch that note's own spaced-rep frontmatter (`last_reviewed`/`next_review`/`ease`, if present) — those stay exclusively a real `/new-session`/`/end-session`'s to set.
   - **B:** append one row to a "JIT Touches" table in that Module's own note — `| date | task unblocked | what was covered |`, same column format as Branch D's Touches table below (create the section, with a one-line header comment, if this is its first use). Distinct from that Module's "Session Notes" (real cut-short teaching only) and "Quiz Log" (real quiz scores only). Never write that Module's own `status`/`next_review`/`interval_days`/`ease`, never touch `Progress-Dashboard.md`. Also bump (or add, if absent) a `last_jit_touch` frontmatter field to today's date — a plain timestamp, not a spaced-rep field, purely so a future `/new-session` can tell this module was actually touched before, without it counting as real progress (see the corresponding read of this field in `new-session.md`, on both its fresh-start and resume paths).
   - **C (new-note case):** create a real `Concepts/` note in that track. It's new, not an existing note, so seed its spaced-rep frontmatter the same way a Branch D note gets seeded (below) — never derive it from Step 5's outcome.
   - **D:** one living note per topic at `Learning/<slug>.md` — not a dated snapshot. Before creating a new file, check existing `Learning/` filenames for a close match and confirm/merge into the existing note rather than forking a near-duplicate. On creation, frontmatter `topic`, `first_learned`, `last_reviewed`, `next_review`, `interval_days`, `ease`, `repo`, `source_session`, seeded with this vault's standard first-exposure defaults — `ease: 2.5`, `interval_days: 1`, `next_review` one day out — the same starting values a new Module gets (cross-check against whatever a new Module's own seed values currently are, if these have since diverged from what's written here). Set `repo` to the repo this was read from; set `source_session` to the open `Work/<repo>/Sessions/` note if a tracked work session is running, else leave it blank (see `Learning/README.md`, which documents these provenance fields and how a merge preserves them). Body: the scope/boundary statement from Step 3, kept visible on every future review (not just stated once), plus a "Touches" table (`date`, `task unblocked`, `what was covered`). On a revisit: append the Touches row and set `last_reviewed` to today. Only advance the schedule — double `interval_days` (capped at 90) and set `next_review` that many days out from today — if the revisit happens on or after the note's current `next_review` date; an earlier touch (the same topic recurring same-day, say) hasn't yet demonstrated longer retention, so leave `interval_days`/`next_review` as they were. `ease` stays frozen at its seeded value permanently; this branch never derives ease from a graded signal, on creation or revisit alike.

8. **Spaced follow-up.** `/new-session`'s Step 1 staleness glance also scans `Learning/` for anything past its `next_review`, nudge not gate, same treatment as the inactive-track check. Because that trigger only fires when a curriculum session is deliberately started, `/learn` itself also glances at `Learning/*.md` on its own invocation and mentions, in passing, anything overdue — never blocking or delaying the current topic. **Also glance at `Work/Owed-Learning.md`** (deferred work-lessons written by `/end-work`) and mention any owed lesson in passing, same non-blocking treatment — these have no `next_review`, they're owed until taken. If the user opts to take one now, teach it from what survives — the `source_session` note's `## Journal` plus the durable notes `/end-work` persisted for it (its `Concepts/`/`Learning/`/`Agent/Patterns` entries), not live git or the original conversation — then clear it per the boundary exception above (remove its row; set that note's `lesson: done`).

9. **Hand control back.** If Step 5 succeeded: close provisionally, not as a flat certification — "you now have what X needs; if that's not actually what was blocking you, say so and we'll re-scope." If Step 7 persisted anything, say what and where in the same breath ("saved as a note under Learning/ — say so if you'd rather this not resurface later"). If Step 5 was opted out of or abandoned instead: close plainly — "we didn't get this fully confirmed — nothing was logged, come back to it if you want another pass."
