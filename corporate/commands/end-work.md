7. **Build the hands-on sandbox and have the user fix it (always, for `type: issue-work`/`feature`).** The PR is merged by now (step 1's precondition), so the accepted solution exists. Skip this step entirely for `routine`/`code-review` (no sandbox — they already completed in step 3). It runs regardless of the lesson choice in step 6 and regardless of whether the start-work pedagogy was escaped.
   - **Source of truth is the merged diff.** The sandbox's reference solution — the "by-default solution" — is the *merged, accepted* PR, not the fix originally proposed; review corrections are part of the answer. The sandbox reproduces the **original state of affairs** (pre-change) and the merged diff is the answer key: for issue-work that's the accepted bug fix; for a feature it's the accepted added behavior, expressed as a **failing acceptance test** the user makes pass (TDD-red, not a reproduced defect). "The gap" means "what the merged PR changed" — well-defined for both.
   - **Review-delta (your discretion).** Where the proposed fix differs meaningfully from the merged one, you may fold that into the brief as a teaching point ("the first approach did X; review corrected it to Y, because…"), sized to how substantive the changes were; skip it when review was cosmetic.
   - **Primary gap.** One sandbox per session, targeting the primary change the merged PR turned on. If several distinct significant changes shipped, pick the most instructive as primary and list the rest in the README as "out of scope for this drill"; `sandbox:` stays single-valued.
   - **Stack.** Match the source repo's language/runtime/test-runner — read its manifest/lockfile/test config (`package.json`, `pyproject.toml`, `go.mod`, `Makefile`, CI config…). Polyglot / multiple runners → match the area the fix touched; still ambiguous → ask. Multi-repo session → use the note's `repo`; still ambiguous → ask. Don't guess.

Reproduce the original state of affairs plus a **failing test that encodes the merged accepted behavior** (the answer key). You write the broken/absent code and that failing test; you do **not** write the fix. If the dir can't be created (permissions, path is a file) → record `sandbox: construction-failed` and report.
   - **Prove it's red before handoff — evidence, not assertion.** Actually run the test and **record the exact command + its red output** in the sandbox README (and the green output after the fix). "I ran it" without the logged output does not count.
   - **Failure outcomes need a shown attempt.** Prefer a smaller-but-faithful reproduction over declaring failure. `construction-failed` (couldn't stand up the harness) and `not-reproducible` (gap is irreducibly infra/environment-specific) may be recorded **only with the attempt shown** — the scaffolding tried and the specific blocking error, or the named irreducible dependency. Never declare either without a demonstrated, logged attempt; that is what stops the outcome from becoming a free skip.

This is a **stricter instance of the Teaching Standard's TS-5** — the user *always* writes the fix and there is no "just fix it" escape here; you may have written the failing test/scaffolding, but never the fix. Stuck → the **TS-6 ladder** with plain, non-cryptic hints (TS-4): hint → reveal+explain → confirm; never paste the fix pre-emptively. Write the brief to the **Teaching Standard** (TS-1 plain + first-principles; cite the real files it references by `repo/path`, TS-2; and **TS-7** — the brief *presents* the picture before the user is gated by writing the fix, so teach-before-gate holds here too, post-merge — see `Teaching-Standard.md`). Self-contained matters: on an escaped or reclassified session the start-work gates never ran, so the sandbox is the user's first structured encounter and can't assume that context. (The brief sets the picture once; it is not a per-step walkthrough, so TS-3 does not bind here.) Frontmatter: `repo`, `source_session`, and links to any `Concepts/`/`Learning/`/`Agent/Patterns/<repo>/` note step 5 wrote.
