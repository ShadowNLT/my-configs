# Resume Work

Picks up a session paused with `/pause-work`. Run this at the start of a fresh agent session.

Knowledge vault root: `{{KNOWLEDGE_VAULT_ROOT}}`
Code Concept Curriculum: `{{CODE_CONCEPT_CURRICULUM_DIR}}` — all teaching and both gates in this session (cite the command at `{{AGENT_COMMANDS_DIR}}/code-concept-curriculum.md` and the twins in that dir). The delivery rules are the same as `start-work.md` step 8: one chunk of prose at a time, one question each, graph order, the term check (CCC G2f) on **every learner-facing line** including the recap and "what's next" (with the internal-word denylist, CCC §2e), the stuck trigger and CCC Phase H, the `## Lessons` rule, and the Phase 4 edit rule: the learner chooses for each step whether to type the change or have you type it, and can switch at any step; a change you typed is replayed against the agreed solution (one plain sentence naming the lesson it applies plus the 2–3 key lines with their location, never a diff), then the tests run, and "Done" comes only after they pass. "Just fix it" skips the replay, not the tests.
Schema reference: `Work/00-How-Work-Tracking-Works.md` in that vault.

1. Determine the current repo (`git rev-parse --show-toplevel`, basename it). If it fails (not a git repo), tell the user and stop.

2. Find the session note under `Work/<repo>/Sessions/` with `paused_at` set in its frontmatter.
   - **None:** tell the user there's no paused session for this repo, offer `/start-work`, and stop.
   - **Migration:** if no `paused_at` note exists but a legacy `Work/<repo>/Handoff.md` sidecar does, fold its body into the referenced session note's `## Handoff` section, set `paused_at` from the sidecar's `handed_off_at`, delete the sidecar, then continue with that note.
   - **Exactly one:** use it.
   - **More than one:** list them (slug + `paused_at`), ask the user which to resume.

3. **Branch check:** compare `git branch --show-current` against the branch recorded in the note's `### Current state` (or the frontmatter `branch`). If they differ, warn the user before continuing — they may have switched branches since pausing — and confirm they want to resume here rather than switch back.

4. Read the note's `## Handoff` section, the `## Pedagogy` section, and the `## Lessons` section — `## Pedagogy` and `## Lessons` record how far the teaching got, and step 7 re-enters at exactly that point. (Legacy: if a `### Pedagogy` block sits under `## Handoff` and the note has no `## Pedagogy` section, move that block verbatim into a new `## Pedagogy` section after `## Lessons` and remove it from `## Handoff`.) **What you say back to the learner never leaks the plan:** first give the pre-flight line (step 6), then 2-3 plain sentences built only from (a) the plain recap of the **passed** chunks (from their `## Lessons` entries and the learner's own answers) and (b) the plain teaching line in `### What's next`, plus the non-teaching state in plain words (e.g. which edit step is next). Never read out chunk ids, the chunk list, `claims:`, gate fields, or the headline of an unpassed chunk. It passes the term check (CCC G2f, §2e). This recap is the one CCC G0 asks for; step 7 does not repeat it.

5. Update the session note in place: clear `paused_at` (blank it), then **re-stamp `agent_id` — but leave `session_uid` exactly as it is.** These two do opposite things on resume:
   - `agent_id` → set to the session identifier exposed by the current harness, because resume runs in a **new** agent session. Add the field if the note predates it; a legacy note may carry this ownership id under the old `session_id` name instead — rename that to `agent_id` as you re-stamp. Re-stamping is what lets a later `/pause-work` or `/end-work` in this resuming session find the note by agent match — the paused note still carries the id of the agent session that paused it, which is no longer this one. If this harness exposes no session identifier, leave `agent_id` blank and use the stable `session_uid`.
   - `session_uid` → **do not change it.** It is the session's stable identity across every handoff; the whole point is that it stays constant no matter how many agents pass the work along. If the note predates `session_uid` and has none, back-fill one now with `uuidgen` (a one-time addition — this is the only place other than `/start-work` that ever writes it), so the resumed session gains a durable id going forward.

   Append a `## Log` line `resumed at <timestamp>`. If the note predates journaling and has no `## Journal` section, add an empty one now (placed after `## Goal`). If it has no `## Lessons` section, add an empty one after `## Goal` too, and if it has no `## Pedagogy` section, add one after `## Lessons` (filled per step 4's legacy move, or empty). Never rewrite existing `## Lessons` entries; only append, per the Lessons rule in `start-work.md` step 8 (plain headline, chunk id only in the trailing `<!-- -->` comment). To match an entry to `passed_chunks:`, read the id from that comment; never show it.

6. Surface the same pre-flight `/start-work` step 3 does — **same one-line, term-checked receipt** (e.g. *"I checked my saved notes from earlier work (N about this project, M open items); nothing in them bears on today's work."*; housekeeping rule in `start-work.md`), then flag only hits relevant to this repo. **Say it before the step 4 recap**, so the recap leads straight into the next part of the lesson:
   - `Agent/Feedback.md` — standing behavioral rules (same as start-work step 3).
   - `Agent/Patterns/<repo>/` (see `Agent/README.md`) — durable facts about how this codebase behaves.
   - `Parking-Lot/INDEX.md` (see `Parking-Lot/README.md`) — filter by repo; open item files under `Parking-Lot/<repo>/` as needed. If a fix for one ships this session, flip its `status` to `resolved` in the item file **and** update its INDEX row.

7. Continue the work described in `### What's next`.

   **If the note's `## Pedagogy` section has a row, re-enter the teaching flow at that point rather than restarting it** (see the Phase 1–4 flow in `start-work.md`). All teaching cites Code Concept Curriculum at `{{CODE_CONCEPT_CURRICULUM_DIR}}`.
   - **Unfinished discovery first.** If the row's `discovery_status` is `pending` or `escalated`, re-enter CCC from that checkpoint (Phases A→F until `clear`, or a fresh escalate), and teach nothing until it is `clear`. A `gate1: passed` on that row is not a pass until discovery is `clear`.
   - **Normal resume (the row has `chunks:` and `passed_chunks:`).** Do not rebuild the graph, do not show it, and do not re-quiz passed chunks. The recap of the passed chunks was given in step 4 (plain prose from their `## Lessons` entries and the learner's own answers, no quiz, term-checked, passed chunks only); do not repeat it. Then rebuild the ready set from `chunks:` minus `passed_chunks:` and serve the first unpassed ready chunk in graph order, exactly as `start-work` Phase 1a (CCC Phase G, resume entry G0). Gates follow `start-work` Phases 1b/3 (CCC Phase I). **Read `stuck_revisits:`** from the row and continue with those counts (CCC H7): a run that already used its stuck revisit escalates on the next stuck instead of revisiting again. A row without the field (written before it existed) counts the `stuck-added` chunks on each side in `chunks:`.
   - **Resuming inside Phase 4** (Gate 2 passed, edits under way): re-enter at the first step that is not "Done" (check `git diff` against the agreed solution, never against memory). Do not assume the learner's earlier choice of who types; ask in one plain line if they have not said. A step that was typed but not yet replayed or tested gets its replay (if you typed it) and its test run before "Done" (`start-work` Phase 4).
   - **Do not re-quiz a `passed` gate** — treat `gate1: passed`/`gate2: passed` as already cleared (`gate2: n/a` when the goal changes no code, such as a review).
   - **Multiple open `item:` rows:** ask which to resume — never pick by recency (same rule as pause/end matching).
   - **Legacy row with no `chunks:` list** (a pause from before chunk saving): do not invent chunks, passes, or claims. When `discovery_status: clear`, run CCC Phase F on the existing graph to rebuild the chunks; when the row has no `discovery_status`, run CCC A→F first. Passes from before the pause do not carry over: teach from the first chunk, except that an existing `gate1: passed` stays passed and its picture chunks are recorded as passed without re-teaching. If the row has `gate1: passed`, `gate2: open`, and no `chunks:`, keep Gate 1 passed, build the solution chunks per `start-work` Phase 2, and teach them. A legacy `procedure: none` or `partial(…)` on an open gate means that gate's teaching was never completed: treat the gate as open and teach it from its first chunk. Any other legacy `procedure:` value is ignored.
   - **Multiple work-items in `## Pedagogy`** (a session that taught+gated issue A, then re-armed for issue B — see the new-issue fork in `start-work.md`): re-enter **each item at its own recorded state**; a `passed`/`done` item stays cleared, an `open` item recaps and continues at its first unpassed chunk per the rule above, an `opted-out` item is not re-taught. Match `gate1: passed`, `claims:`, `chunks:`, and `passed_chunks:` to the item they belong to — never to the wrong issue.
   - **A materially-different issue surfacing after resume** is handled exactly as in `start-work` (the new-issue fork): stop, surface **work-now vs park**; if worked, its fix-edit is blocked until its picture and solution chunks are taught and passed.
   - **If there is no Pedagogy row at all** (a legacy paused note from before this checkpoint existed), say so and reconstruct minimally from the `## Journal` rather than assuming which gates were passed — still **do not invent `claims:` or passes**.

   Follow the **Journal Protocol** (see `Work/00-How-Work-Tracking-Works.md`) for the rest of this session, exactly as `/start-work` does: append a typed `## Journal` entry at each trigger event (a domain fact learned, a root cause identified, an approach chosen, an approach abandoned), and append each passed chunk to `## Lessons` per the Lessons rule in `start-work.md` step 8. This must be carried here too, because a session that spans a pause/resume runs its second half in this fresh chat, and without this the record would go dark after the resume. Reminder for the rest of this session (from global rules): never add an AI co-author trailer to commits, never stage `.agent/` into this repo, and if the conversation starts running long again, offer `/pause-work` before pushing through.
