# Start Work

**Mandatory protocol — read before doing anything.** Every step below is required and runs in order, exactly as written, on every invocation, regardless of which agent is running this command. This is not a menu of suggestions: do not skip a step, reorder steps, or improvise around them. The git-flow branch setup in step 6 in particular is non-negotiable — never start work on the current branch, never skip the fresh pull of the base branch, and never invent an ad-hoc branch name. (The one exception is a code-review session, which is read-only and cuts no branch: see step 4b and step 6.) If any step genuinely cannot be completed (e.g. a dirty working tree blocks the checkout, or a required convention is missing), **stop and ask the user** — do not work around it silently.

Knowledge vault root: `{{KNOWLEDGE_VAULT_ROOT}}`
Teaching Standard: `{{TEACHING_STANDARD_PATH}}` — read §Procedure for every load-bearing teach moment.
Schema reference: `Work/00-How-Work-Tracking-Works.md` under that vault root.

1. Determine the current repo: run `git rev-parse --show-toplevel` from the working directory. If it fails (not a git repo), tell the user and stop — this command only applies inside a repo. Derive `<repo>` as the basename of the toplevel path. Note the *starting* branch and whether the working tree is dirty (`git branch --show-current`, `git status --short`) — you'll cut a fresh working branch in step 6, and the note records that one, not this.

2. Check for a prior session that bears on this one — a **paused** session to resume, or a **completed** session this work follows up on. Look under `Work/<repo>/Sessions/`.
   - **Paused** (a note with `paused_at` set, or a legacy `Work/<repo>/Handoff.md` sidecar): don't resume it inline. Tell the user there's a paused session, summarize its `### What's next` in one line, and point them to `/resume-work`. Ask whether they'd rather resume that (→ stop, they run `/resume-work`) or start a genuinely fresh session anyway (→ continue to step 3; leave the paused note untouched — it's theirs to resume or `/end-work` later).
   - **Follow-up to completed work** — if the user says this continues earlier work that already shipped (its note is `status: completed`): treat it as a **new linked session, never a reopen** (a completed note is a one-time record; its terminal fields are settled and `/end-work` won't reopen it).
     - **Locate the prior note** from the user's description — search `Work/<repo>/Sessions/` on goal text / branch / ticket id / PR number. **Confirm before linking:** state the single best match and confirm it; if several match, list them (`goal`, `started_at`) and ask; if none is locatable or the prior work was never tracked, say so and proceed as a plain unlinked session.
     - Once confirmed, set `continues:` in the new note's frontmatter (step 7) to `<prior session_uid>  [[<prior note path>]]`. The link is **one-directional** — the prior completed note stays **frozen** (not edited). Context flows by *reading* it: seed step 4's picture **warm** from the prior note's `## Decisions` / `## Follow-ups` / `## Journal`, on top of the durable facts `/end-work` already pushed to Patterns/Concepts/Learning (surfaced in step 3). If the prior note itself carries a `continues:` chain, follow it toward the most-recent relevant ancestor as needed; **never loop** — stop if you revisit a `session_uid`. Cross-repo is not followed (notes live under this repo's `Work/<repo>/`).
     - If this follow-up was **queued** as a `Parking-Lot/<repo>/INDEX.md` entry or a `## Follow-ups` line in the prior note, **close that origin** once the new session note exists — flip the Parking-Lot entry's `status` to `resolved`, or strike the follow-up line with a pointer to the new session — so it stops re-surfacing in future pre-flights.
   - **Other agents' in-progress notes are not yours to touch:** an `in-progress` note owned by a *different* `agent_id` is left alone — just start your new session. (The ownership match in `/pause-work`/`/end-work` is what keeps concurrent sessions from colliding; a new issue re-arming teach→gate is scoped to *your own* running session, not another's note.)
   - If none of these apply, continue to step 3.

3. Check these vault corners and surface anything relevant briefly ("heads up, from a prior session: ...") if it bears on what's about to happen. Say nothing if there's no relevant hit — don't force a mention.
   - `Agent/Feedback.md`: standing behavioral rules (git/PR/CI/web3/vault workflow) that fire on specific actions. Not repo-scoped; read it every session so the action-triggered rules are in hand before any git/PR/web3 work. (Always-on rules like writing style and edit scope live in AGENT.md and are already loaded.)
   - `Agent/Patterns/<repo>/` (see `Agent/README.md`) — durable facts about how this codebase behaves.
   - `Parking-Lot/<repo>/INDEX.md` (see `Parking-Lot/README.md`) — real issues noticed in passing and deferred, not yet fixed. Distinct from `Agent/Patterns/`: don't conflate the two when reading or later writing to either. If the session's stated goal turns out to touch something with an open Parking-Lot entry, flag it before starting; if a fix for one ships during the session, flip that entry's `status` to `resolved` in place rather than leaving it stale.

4. **Classify the session and run the matching pre-work protocol before determining the goal or touching anything.** Say the type in one line first, so a wrong read is easy to correct. The four types are mutually exclusive:

   **a. Routine / mechanical** (a concrete change whose end-state is already given: a version bump, a rename, a mechanical refactor with no design decision). Take the goal from `$ARGUMENTS` or the user and proceed. **Runs the comprehension-gated tutorial (step 8) like 4c/4d, but with *proportionate* content — the picture and gate are sized to how non-obvious the change is: a one-line rename gets a one-clause why and a single light check, never a manufactured lesson about nothing. Phase 4 still applies (you write the edit).** Cuts a branch in step 6. Earns **no** `/end-work` sandbox — that stays gated on `type:` = 4c/4d.

   **b. Code review** (reviewing a PR or diff, not changing this repo's code). Before forming any verdict or posting any comment, build the picture first:
   - Understand, from first principles and against the *actual code* (not just the PR description, which is often incomplete or wrong), what problem the change solves and how. Read the real files.
   - **State of affairs, required when correctness depends on something outside the diff** (it touches config, a service boundary, or a contract or value consumed by another service or repo): look beyond the diff before judging. Is the runtime or a consumer in another repo, is there a companion or sibling PR on the same ticket, does deploy ordering matter. Never review a diff in isolation when its correctness lives partly outside it.
   - A review is read-only: it cuts no branch (step 6), and you never switch a shared checkout just to review. The goal (step 5) is "review PR #<n>". There is nothing to edit, so the escape hatch here is simply the bottom-line request: if the user only wants the verdict, skip the step-8 diff-comprehension gate and give it without the full walkthrough (see step 8).

   **c. Issue-work** (something is *wrong* and the cause is not yet known: a bug or unclear/broken behavior). Say so in one line, e.g. *"This looks like a bug, let's work through it before I touch anything (say 'just fix it' to skip the walkthrough)."* Then run the loop before determining the goal:
     a. Describe the issue together, restate it in plain terms so both people are aligned.
     b. **Teach the picture (0→100)** — root-cause, first-principles: present *why* it exists, understandable standalone, to the **0→100 standard** (below). **This is the teach moment; TS-7 requires it to happen before any gate runs this session** (Gate 1 is in step 8). Run **Teaching Standard §Procedure** (`{{TEACHING_STANDARD_PATH}}`) at full 0→100 depth — not a summary.
     c. Point at the specific files/functions (reading pointers only; reading/grepping to build the analysis is fine, writing is not).
   The restated issue becomes the session goal (skip step 5's goal question).

   **d. Feature / code change** (deliberately building or changing intended behavior, with no defect to diagnose). Before editing, establish and present two things, then wait for go-ahead:
     - **State of affairs, to the 0→100 standard (below):** how the relevant code works today and its surrounding context (reading only to establish it).
     - **What the ticket is trying to solve:** restate the goal in plain terms. This becomes the session goal (skip step 5's goal question).

   **The 0→100 standard (types c and d only).** Whichever the type presents — 4c's root-cause analysis or 4d's state of affairs — run **Teaching Standard §Procedure** (`{{TEACHING_STANDARD_PATH}}`) P1–P6 at full depth: terminal concept → prerequisite chain → knowledge-graph reconcile under `{{KNOWLEDGE_VAULT_ROOT}}` (P3: search `Concepts/`/`Modules/`/`Learning/`, teach only the delta, link back) → knowledge map (P4) → **invoke `/explain-first-principles`** for P5 (never free-hand) → `/layman-terms` only as P6 if needed. **Read-only** here; persistence is `/end-work`'s job. Do **not** apply full 0→100 to 4b — use §Procedure at proportionate depth only. Compact trigger: `Teaching Standard §Procedure + TS-1 + TS-2 + TS-4` — see `{{TEACHING_STANDARD_PATH}}`.

   **Discriminator for c vs d:** is there a defect to diagnose (c), or are you building intended behavior (d)?

   Types **c** and **d** are hard-gated identically:
   - **Gated:** editing source-controlled files, and state-mutating git operations (commit/checkout/reset/stash). None happen until explicit go-ahead, even if the change seems obvious or small.
   - **Taught-first precondition (TS-7 — the enforcement backstop):** go-ahead to edit a fix for an issue is **blocked until that issue's 0→100 picture and solution were presented *this session*** (its Phases 1–3 ran). Teaching therefore can't be skipped — the fix needs an edit, and the edit is gated on the teaching — rather than relying on remembering to teach. The only bypass is the per-item escape hatch below. See `{{TEACHING_STANDARD_PATH}}` TS-7.
   - **Not gated:** reading code, grepping, running tests, installing deps, starting/restarting servers, read-only git. The investigation needed to describe the issue and build the analysis is always fine.
   - **"Explicit go-ahead" means:** an affirmative directive ("go ahead," "do it," "fix it," or an escape phrase) that names or unambiguously references a specific proposal already on the table. Scoped only to the exact diff discussed — an adjacent "obviously needed" change (a nearby rename) needs its own separate go-ahead. Naming a fix-applying skill directly (`/code-review --fix`, `simplify`) counts as go-ahead for that skill's own scope.
   - **Escape hatch (c and d only):** the user saying "just fix it" / "just build it" / "skip the loop," up front or mid-loop, exits the walkthrough *and* counts as go-ahead for that specific change. It is a per-instance bypass, not a standing override, and you never skip the loop on your own read of what's "trivial" — the genuinely mechanical case is type **a**, decided at classification.

5. Determine the goal: for issue-work (4c) or feature (4d) sessions, use the restated goal from step 4; for code review (4b), it's "review PR #<n>". Otherwise (routine/mechanical, 4a) use `$ARGUMENTS` if given; otherwise ask the user in one line what this session is for. Don't over-interrogate — one question, move on.

6. **Set up the working branch (mandatory git-flow — do this before creating the session note, so the note records the branch work actually happens on).** Runs for every fresh session, with two exceptions: the user chose in step 2 to resume a paused session (that's `/resume-work`'s job), or step 4 classified this as a **code review** (4b), which is read-only, so leave the checkout on its current branch, never switch a shared checkout just to review, and skip straight to step 7. Routine/mechanical (4a), issue-work (4c), and feature (4d) sessions all cut a branch normally.
   a. **Pick the base branch:** prefer `develop`; if the repo has no `develop`, use `main` (or `master`); if it has none of these, ask the user which branch to base off. Check with `git branch --list develop main master` and `git branch -r`.
   b. **Switch to the base and pull it fresh:** `git checkout <base>` then `git pull`. **Leave any uncommitted local changes exactly where they are** — do NOT stash, commit, or discard them; git carries them across the checkout. If the checkout is blocked because local changes would be overwritten, **stop and tell the user** — never force it or throw away their work.
   c. **Cut the new branch off the fresh base:** `git checkout -b <new-branch>`. Any uncommitted changes ride along onto the new branch — that is intended ("leave them where they are").
   d. **Name the branch by the repo's documented convention, never an ad-hoc guess.** Read `Agent/Patterns/<repo>/git-branch-and-commit-conventions.md` (already surfaced in step 3) and follow it exactly. For `vivenu-core`: `AFG-####/kebab-case-slug` for `AFG-` tickets (ticket ID as the prefix, slash, no `feature/` wrapper), and `feature/<ticket-id-lowercase>-<slug>` for other prefixes (`TBT-`, `SPX-`, ...). Derive the slug from the goal. Get the ticket ID from the goal / `$ARGUMENTS` if present, else ask the user for it. If the repo has no conventions file, **ask the user for the naming pattern** rather than inventing one.
   e. Use this new branch as `<branch>` in the session note below, and confirm the switch to the user in one line (base pulled → new branch created).

7. Create `Work/<repo>/Sessions/<YYYY-MM-DD-HHmm>-<slug>.md` (slug derived from the goal, kebab-case, short) with:
   ```yaml
   ---
   repo: <repo>
   branch: <the new branch created in step 6>
   type: <routine | code-review | issue-work | feature>   # = classification 4a/4b/4c/4d from step 4
   started_at: <timestamp>
   ended_at:
   status: in-progress
   session_uid: <stable unique id for this session, generated once here with `uuidgen` and never changed — agent-agnostic, survives every handoff>
   agent_id: <the current harness's session identifier, or blank if it exposes none>
   goal: <goal>
   db_baseline: none   # none | captured | restored — the local dev-DB snapshot lifecycle (see step 8's DB Baseline Protocol and /end-work's restore step)
   continues:          # optional — set ONLY on a follow-up session: <prior session_uid>  [[prior note path]]. One-directional; the prior completed note stays frozen (see step 2). Omit otherwise.
   ---
   ```
   For a **code-review** session (4b) no new branch was cut: set `branch:` to the checkout's current branch with a `(read-only review, no branch cut)` note, and keep the PR under review in `goal:`.

   `type:` records the step-4 classification and is what `/end-work`'s sandbox gate reads to decide whether this session earns a hands-on sandbox (only `issue-work`/`feature` do). **It is not frozen:** if the session's character materially changes — a `feature` that turns out to be diagnosing a defect, or a `routine` that becomes real issue-work — update `type:` in place and say so in one line, so a routine-turned-issue-work session correctly earns its sandbox later. (Taking the "just fix it" escape does *not* by itself change `type:` — the field tracks the *nature* of the work, not whether the pedagogy ran.) **Note invariant:** this note is created for every session type, unconditionally, before any pedagogy or gating below — the record is mandatory; only the teaching is ever skippable.

   These are **two different id fields with two different jobs — do not conflate them**:
   - `session_uid` is the note's **stable identity**. Generate it **once, here, at note creation** — run `uuidgen` and paste the value — and then **never change it again**: not on pause, not on resume, not when a different agent takes over. It is what uniquely names *this work session* regardless of which agent is driving now or drove earlier. It's generated the identical way for every agent, so it is fully agent-agnostic and not tied to any one tool's environment variable. If `uuidgen` is somehow unavailable, fall back to any unique token (e.g. the note's `<YYYY-MM-DD-HHmm>-<slug>`), but prefer a real UUID.
   - `agent_id` identifies the agent session that **currently owns** the note — the one running right now. Each agent stamps the session identifier exposed by its current harness. This is the field `/pause-work` and `/end-work` **match on** to act on *this* agent session rather than whichever in-progress note is newest, and it is **re-stamped on every `/resume-work`** because resume runs in a new agent session. If the harness exposes no session identifier, leave `agent_id` blank and note it to the user — `session_uid` still uniquely identifies the session.
   Sections: `## Goal` (filled), `## Journal` (empty — the running capture; see the Journal Protocol in `Work/00-How-Work-Tracking-Works.md`), `## Log` (empty), `## Files Touched` (empty), `## Decisions` (empty), `## Follow-ups` (empty), `## DB Baseline` (empty — the local dev-DB snapshot record; see the DB Baseline Protocol at the end of step 8).

8. Confirm to the user in one line: repo, branch (or the PR under review, for code reviews), goal, and the session note path. Then proceed with the actual work:
   - **Code review (4b) — teaching, then verdict (no code part).** Build the step-4b picture via **Teaching Standard §Procedure** at proportionate depth (`{{TEACHING_STANDARD_PATH}}`), then **gate your comprehension of the diff before forming any verdict:** run the **TS-6 gate/reveal ladder** (restate what the change does and why + a correct why/how follow-up; plain no-hints-first hints TS-4; terminal states pass or pause — see `{{TEACHING_STANDARD_PATH}}`) on that picture. There is **no Phase 4** — a review edits nothing, so TS-3/TS-5 do not fire; this is teaching to confirm you understood the context, not a walkthrough of edits. **Escape hatch:** "just the bottom line" / "just the verdict" skips the gate and goes straight to the verdict — this is 4b's form of the bypass, and it preserves the read-only "give the verdict without the full walkthrough" path. Posting comments, approving, or requesting changes is publishing, so confirm the exact text with the user before posting.
   - **Editing sessions — routine (4a), issue-work (4c), feature (4d), no escape phrase used — the comprehension-gated tutorial.** Run these phases in order. Phases 1–3 are read-only (reading/grepping/running tests is fine; no source edits, no state-mutating git). Editing begins only in Phase 4. **For 4a, run the whole ladder *proportionately* (see 4a in step 4): build a small picture and a light gate, never a fabricated lesson; Gate 1 and Gate 2 may collapse into a single check when the change *is* its own solution.** **All teaching below runs under `{{TEACHING_STANDARD_PATH}}` — compact trigger: §Procedure + TS-1 + TS-2 + TS-4.**
     - **Phase 1a — Present the picture (TS-7).** Present — or, on resume, **re-present** — the 0→100 picture from step 4 and the issue/goal, via §Procedure (already run in step 4 for 4c/4d; re-run P5–P6 if resuming). **Never run Gate 1 until this has happened *this session*:** presentation is not durably checkpointed, so a resumed session re-presents before gating (see `{{TEACHING_STANDARD_PATH}}` TS-7).
     - **Phase 1b — Gate 1 (the picture + the issue).** Run the **TS-6 gate/reveal ladder** on the just-presented picture and the issue/goal (see `{{TEACHING_STANDARD_PATH}}`). Hints are **no-hints-first** (only after a miss) and plain, never cryptic (TS-4). Never advance without a pass, never write code as a fallback; if the user still can't pass after a reveal, that signals fatigue → offer `/pause-work`, not to proceed.
     - **Phase 2 — Present the intended solution** at concept level (the approach, why it resolves the issue, the alternatives rejected). Still read-only. Run §Procedure P1–P5 on the solution (proportionate for 4a).
     - **Phase 3 — Gate 2 (the solution).** Run the same **TS-6 ladder** as Phase 1b, now on the intended solution. **(TS-7: on resume, re-present the Phase-2 solution before running this gate — Gate 2 tests material that must have been presented this session.)**
     - **Phase 4 — Tutorial walkthrough.** The learner is now editing real code, so **TS-3 and TS-5 fire — say so in one line as Phase 4 opens.** Decompose the solution into ordered steps; do one at a time and do not advance to step N+1 until step N is finished. **Reaching Phase 4 (Gate 2 passed) *is* the go-ahead** — the user drives the edits themselves, so no separate "go ahead?" is needed. For **each step**:
       - **Lead with the why-here (TS-3):** open the step with *why this file* and *why this edit here* before any mechanics — proportionate to how non-obvious the choice is (one clause for a self-evident step, the full reason for a load-bearing one). Cite the file by `repo/path` (TS-2). This holds for **every** step, simple or not — the user never applies an edit without knowing why it goes there.
       - **You write the production code (TS-5):** the user supplies the step as **pseudo-code in chat or real code they write into the file themselves**; you **verify and correct, and may write complementary tests/fixtures/scaffolding — but you do not write the production change itself** (the fix/feature logic is theirs; don't route it through a "helper" or test). Write it yourself only if they explicitly ask — "just fix it" counts. See `{{TEACHING_STANDARD_PATH}}`.
       - For a step you judge *simple*, still lead with the brief why-here, then ask the user to attempt it; for a non-trivial step, give the fuller why + approach, then the user implements.
       - Stuck on a step → the **TS-6 ladder** with plain, non-cryptic hints (TS-4): after 4–5 failed attempts, reveal+explain, have the user apply it, confirm. Terminal states: the step gets done, or the session pauses; never a silent skip.
   - **Escape hatch (all editing sessions — 4a/4c/4d, sole bypass):** the user saying "just fix it" / "just build it" / "skip the loop", up front or mid-loop, exits the whole sequence and counts as go-ahead for that specific change. **Only for 4c/4d**, add one line on escape: *"note — the hands-on sandbox at `/end-work` still runs"* (the sandbox is gated on `type:` = 4c/4d, so it fires regardless of the escape); **do not add this note for a 4a escape — 4a earns no sandbox.** Never silently skip the tutorial on your own read of "too trivial": for genuinely mechanical 4a work the answer is *proportionality* (a small picture, a light gate), not omission.
   - **Nothing teachable to gate against** (e.g. a pure config/data edit with no mechanism to understand): keep the picture and gate proportionate to near-zero — state the one-clause why, do the Phase 4 edit, and don't manufacture a quiz. This is proportionality at its floor, **not** a fourth bypass; the "just fix it" escape above remains the only bypass.

**New issue mid-session (TS-7 fork).** If a *materially-different* issue surfaces while you work — a distinct defect/behaviour, not a clarification of the current one — **do not silently fold it into the current work** (that is the exact failure TS-7 exists to stop). Stop and put the fork to the user: **work it now** → run its own teach→gate (present its 0→100 picture, gate it) before its fix-edit, which the taught-first precondition (step 4's hard-gate) blocks until then; or **park it** → a one-line `Parking-Lot/<repo>/INDEX.md` entry, no teaching, and carry on. The per-item "just fix it" opt-out skips teaching for that one item only (not a standing off-switch). This re-arm is scoped to *your own* running session and never reaches into another agent's note. "Materially-different" is a **different axis** from `type:`-not-frozen — a new issue may or may not change `type:` — judge them separately. See `{{TEACHING_STANDARD_PATH}}` TS-7.

**DB Baseline Protocol (local dev-DB snapshot + restore).** During the work you may change the **local** dev DB purely to exercise the change — seed a user/org, insert a fixture, flip a feature-flag row, backdate a record. So those changes can be undone later, the mechanism is **snapshot-and-restore**, not per-change tracking: capture a baseline *before* the first such change, and `/end-work` restores to it at close (see `end-work.md`).
   - **When.** Before you first mutate the local dev DB for the work (lazily at first need is fine; eagerly at session start is also fine) — never after, or the mutation is already baked into the baseline.
   - **Disposable-local guard (required).** Snapshot only a genuinely **local, disposable** dev DB. If the target is shared/staging/remote, do **not** snapshot or plan a restore — tell the user and skip (`db_baseline` stays `none`); restoring shared infra would destroy other people's data.
   - **No-op cases.** Repo has no local DB, or the DB is **ephemeral** (recreated each run — a throwaway Docker container, a `db:reset`-on-boot setup): skip entirely, `db_baseline` stays `none`, mention it once. **Emptiness is valid — never nag** (mirrors the Journal's contract).
   - **How.** Use the repo's own tooling (`pg_dump` / a `db:dump` script / a Docker volume or `docker compose` snapshot). Record in `## DB Baseline`: the DB target(s) and store type, the snapshot handle/path, the exact capture command, and the `date`. Set `db_baseline: captured`. **Multi-store:** snapshot each local store the session will touch. **Machine-local:** the snapshot lives on *this* machine — say so in the record, so a cross-machine `/resume-work` knows it cannot restore here.
   - **Restore** is `/end-work`'s job (and the on-prompt "restore the dev DB" — a full reset to baseline, confirmed first because it discards *all* session dev data, not just the setup rows). This section is the record those read; it is blunt by design — restore returns the DB to its start-of-session state.

Follow the **Journal Protocol** (see `Work/00-How-Work-Tracking-Works.md`) for the rest of this session: as you work, append a typed entry to the session note's `## Journal` at each trigger event: a domain fact learned, a root cause identified, an approach chosen, an approach abandoned. This is what lets `/end-work` (and any later lesson) work from a real record rather than an end-of-session reconstruction.

Reminder for the rest of this session (from global rules): never add an AI co-author trailer to commits, never stage `.agent/` into this repo, and if the conversation starts running long, offer `/pause-work` before pushing through.
