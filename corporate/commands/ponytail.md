# Ponytail

Target: $ARGUMENTS — or, if empty, the most recent plan, requirement, or diff in this conversation. If it's ambiguous which one that is, ask rather than guess.

## When to use
Right before implementation starts, once a plan or requirement exists — or against a diff already in progress. Run it as the last check before finishing a change, or any time you notice you're about to add an abstraction, parameter, or generalization that wasn't explicitly requested.

## Relationship to code-pi
This skill decides what's safe to cut, narrow, or add in the smallest shape — none of these are safe to judge from the task's literal ask alone when blast-radius information isn't already in hand. Run `/code-pi` first (it applies just as well to a proposed addition — a new parameter, a new field, a new case in a shared dispatch table — as to a removal) or do equivalent diligence (callers, exports, dynamic dispatch, external consumers): grep the symbol/function name repo-wide as a cheap first pass; more than a handful of call sites, or it's exported from a shared/common package, both count as a wide audience. Count the call/render sites directly; don't let export status stand in for that count. **Export breadth is not call-site breadth**, and app-local is not single call site: a component or function local to one app (exported nowhere) can still render or be called at many sites, so "not exported" is never proof of "one caller." When a change alters *conditionally-rendered or context-sensitive* output/behavior (step-specific UI, a gated branch, tenant- or locale-specific output) of a symbol with more than one call/render site, minimality is per site: the smallest-yet-correct shape gates the change at each site that needs it, and "correct on the one surface I had in mind" is not correct. code-pi step 2 does the enumeration (its sampling disclosure applies for high-fan-out symbols: cover each distinct rendering context, not every raw site); walk those sites and state whether the change is correct at each, and treat a mismatch between site count and the requirement's intended scope (four render sites under a "details-step only" requirement) as the red flag. A uniformly-correct change (a shared bug fix, a behavior-preserving refactor), a single-use symbol, or a leaf edit skips this walk. A surface with a small, contained audience: judge minimality against the task. A surface with a wide or unknown audience — including when you can't actually determine how wide it is — judge minimality against that audience instead, even if today's task only needs one flag, one branch, or one caller. (E.g.: a new optional flag on a shared formatter, an added field on a widely-imported type, a new branch in a central dispatch table — not just deletions.) Don't cut something on "nothing local uses this" alone. Step 2 below refers back to this diligence explicitly for cuts, and step 4 does the same for addition-shape decisions — neither is a separate, softer check.

## Process

**1. State the actual requirement in one sentence**, stripped of any generalization you're tempted to add right now, for this task. This isn't the same as stripping a generalization someone already decided and ticketed elsewhere — if the codebase or plan already commits to a piece not yet wired up, that's not a live temptation to resist, it's committed work in progress. And it isn't the same as something requested earlier in this same conversation or ticket but not yet visible in the diff you're looking at — check the fuller context before calling something "unrequested," not just the diff in isolation.

**2. Ask, in order:**
- Does existing code or config already cover this?
- Can the requirement be met by deleting something instead of adding — only once you've done the blast-radius diligence from the Relationship note above, and only after checking for a nearby signal (a comment, a ticket reference, a recent related commit) suggesting the "unused" piece is actually a committed-but-not-yet-wired-up contract, not dead code. If no such signal exists, you can still recommend the cut, but say so explicitly — disclose that no corroborating signal was found rather than asserting confidence you don't have.
- Is there a narrower patch that satisfies exactly what was asked?

**Paint / show-through signal (Step 2):** An inline comment or nearby note that parent-only / show-through is insufficient (or that a style must stay on the paint surface) is a strong signal against cutting. It does **not** permanently veto a cut that later passes the Step 4 paint-surface verification below; if the comment still disagrees after a passing check—or you cannot verify—do not cut on your own say-so: list pending in Output and quote the comment.

**Exception:** non-functional security or correctness requirements — authorization, rate-limiting, input sanitization, fixing sibling instances of a reported vulnerability class, and similar controls — are not "generalization" even when the request didn't name them. They're part of a correct implementation, not an addition to a minimal one. Don't narrow past them. If something could plausibly be read as either a security control worth keeping or an unrequested generalization worth cutting, default to keeping it — the cost of an unnecessary line is much lower than the cost of a silently missing control.

Tests that assert real, still-applicable behavior aren't fair game for trimming under this exception either — a test guarding code you're keeping isn't "unrequested." A test for code you're deliberately deleting elsewhere in the same change is fine to remove along with it.

**3. If a diff already exists**, scan it for unrequested abstractions, speculative parameters, defensive handling for cases that genuinely can't occur, and logic that duplicates existing logic elsewhere — an extracted helper, or a third occurrence of the same inline pattern that's never been extracted. Don't wait for a helper to already exist before flagging repetition. Treat a scope-narrowing edit (checking fewer fields, cases, or inputs than before) the same as an outright deletion for the purposes of step 4's escalation below — narrowing a check is a partial removal, not a neutral modification. Before recommending dedup of duplicated or "overridden" visible styles, apply the paint / compositing gate in Step 4.

**4. Propose the smallest viable version.** "Smallest" means smallest conceptual/maintenance footprint, not smallest line count — reusing an existing pattern or extension point can beat a shorter one-off that breaks convention, unless that pattern is already known to be deprecated or on its way out. For a brand-new addition with no existing pattern to reuse, the same blast-radius diligence from "Relationship to code-pi" above governs how minimal a shape to propose — don't default to the leanest form just because today's task only needs one case. If the task itself is a removal or cleanup, "smallest" means the smallest diff that still removes everything asked for — orphaned call sites, dead imports, and stale flags or tests left behind don't count as minimal just because the diff looks small; completeness wins over size for this shape of task.

Name explicitly what was cut and why it's safe to omit, and confirm the result still satisfies the one-sentence requirement from step 1 — re-read that sentence and check the proposed cut against it directly, word by word, rather than asserting compliance in passing.

For any cut or narrowing that touches a check on external input, a public API boundary, or any trust boundary: don't cut it on your own say-so. Flag it for explicit human confirmation instead — "no current caller violates this" can't be verified against callers that don't exist yet, and a confident-sounding rationale here tends to make a reviewer *less* likely to double check, not more. A flagged-but-unconfirmed cut stays in place: don't implement it, and don't let later steps or downstream reasoning treat it as already gone until a human actually confirms it.

**Paint / compositing (Step 4):** Before removing a class or style that appears redundant with an ancestor—or consolidating a child override "up" onto a themed ancestor:

1. Matching tokens on parent and child are never sufficient proof the child's copy is safe to drop.
2. A **different** child token (e.g. fixed `bg-gray-100` under a themed ancestor `bg-muted`) is also not fair game to "dedupe upward." That is often an intentional override so the surface stays theme-invariant; consolidating onto the ancestor reintroduces theme tokens onto the paint surface.
3. CSS on an ancestor does **not** paint onto a replaced/paint surface that composites its own pixels (notably `<canvas>`; similarly `video` and other self-compositing surfaces). Token match or "host has the class" ≠ the surface looking the same.
4. **Where ownership may live:** For self-compositing surfaces (3), the style must stay on **that element** unless verification proves it is unnecessary—do **not** treat the wrapper/host as an equivalent owner. For ordinary boxes, the element or its direct host may own the style.
5. If the cut touches styles on a user-visible paint surface: you may implement the cut only after verifying that **surface** still looks correct **after** the change. Verification means a **live UI / browser** (or equivalent visual harness) check—not unit/jsdom tests, mocked drawing libraries, or code-reading. Cover every theme mode that surface actually uses (at minimum light and `.dark` when a `.dark` / seller-`bodyBgMode` path exists; seller dark is not optional if the product has it). If you cannot run that check in this run → do **not** cut; flag for human confirmation; list in Output as pending (same pattern as trust-boundary cuts).
6. **Single owner (after proof):** When parent-only is proven by (5) for an ordinary box, put the style on one node and remove the other. When cutting an ancestor style a surface may rely on, promote onto the correct owner per (4) first, then remove the ancestor—only after (5). When not proven, keep the style on the paint surface (self-compositing: on that element; ordinary box: element or direct host) and do not dedupe upward. Flag kept duplicates / overrides in Step 5.

**Verified-fix protection (Step 4):** Do not cut, on theory alone, lines that are the live subject of the current requirement/diff's verified visual or behavioral fix. "Verified" = an explicit check recorded in this conversation or ticket for this requirement (user confirmation, acknowledged screenshot, or passing targeted test)—not pause/resume session memory. If it is unclear which lines are the fix, treat the whole touched component/surface as protected. Either re-verify per paint/compositing (5) after the cut or leave the lines and list the skipped cut in Output as pending human confirmation.

**5. Flag any place where "smaller" trades off against clarity, robustness, or future consolidation cost** (e.g., three similar narrow patches instead of one shared abstraction) — even when step 4 concluded the plan is already minimal and there's no cut to attach the flag to. This step always produces output, even when it's "no tradeoffs found." Include kept paint-surface duplicates / theme-invariant overrides flagged by the Step 4 paint gate.

**Grounding a flagged tradeoff (Step 5):** For any flag that asserts a concrete failure scenario or rests on a checkable premise — a robustness or correctness-adjacent risk, or a future-consolidation claim like "there are already three copies of this pattern" — confirm it against the actual structure before stating it as real: check the relevant callers, portals, guards, render/stacking order, or occurrence count. This is the same grounding step 4 demands before a paint/stacking cut, with one difference in what happens when it fails. Unlike a step-4 cut, an unverifiable tradeoff is **not** withheld: still surface it, but label it "Unconfirmed:" (or "have not checked X") rather than state it as an established risk. A confident risk flag is more likely to be acted on than re-checked, so labeling an unverified one as theory beats asserting it as fact. Where the flag is about how a surface actually paints or looks, the bar is step 4's paint-gate standard (a live UI check, not code-reading); where a structural guarantee settles it (e.g. a portal that always renders last), confirming that structure is enough. Pure clarity or aesthetic tradeoffs ("this reads worse") are judgments with no failure path to verify — own them as judgment, don't assert them as fact and don't gate them on a code check.

## Output
Either "the current plan is already minimal" or a revised, smaller plan with the deltas named. Either way, always include: any tradeoffs flagged in step 5, and any cuts or narrowings flagged in step 4 as pending human confirmation — clearly marked as not yet approved, not folded into the delta list as if already decided.
