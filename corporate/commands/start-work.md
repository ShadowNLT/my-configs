# Start Work

**Mandatory protocol — read before doing anything.** Every step below is required and runs in order, exactly as written, on every invocation, regardless of which agent is running this command. This is not a menu of suggestions: do not skip a step, reorder steps, or improvise around them. **There is one playbook.** Every call runs the same flow: teach the picture with Code Concept Curriculum, teach the solution the same way, do the work, save. There are no session types and nothing branches on one. The git-flow branch setup in step 6 in particular is non-negotiable — never start work on the current branch, never skip the fresh pull of the base branch, and never invent an ad-hoc branch name. (The one exception: when the goal changes no code in this repo, such as reviewing someone else's PR, no branch is cut — see step 6.) If any step genuinely cannot be completed (e.g. a dirty working tree blocks the checkout, or a required convention is missing), **stop and ask the user** — do not work around it silently.

Code Concept Curriculum: `{{CODE_CONCEPT_CURRICULUM_DIR}}` — cite and obey for all teaching in this session: the picture, the solution, both gates, hints, and a stuck learner (Phases A→I plus the solution extension, Phase S). Read the command at `{{AGENT_COMMANDS_DIR}}/code-concept-curriculum.md` and the twins in that dir (`code-concept-curriculum.md`, `code-concept-curriculum-algo-sketch.md`). Do not replace them with a summary, and do not paste them here.
Layman-terms denylist: `{{AGENT_CONFIG_DIR}}/layman-terms/denylist.txt` — used by the term check (CCC G2f) on every piece of learner-facing text, together with CCC's internal-word denylist (CCC §2e).
**Learner-facing text** means every line the learner sees in this session, not only the lessons: the restated goal and the teach-first line (step 4), the pre-flight line (step 3), the branch line (step 6e), the confirm line (step 8), every chunk, question, hint, stuck-added chunk and solution chunk, the walkthrough (Phase 4) including each replay of an edit you typed, its closing question, and each "Done" line, and anything said on pause, resume or end. All of it passes the term check in step 8 before it is shown.
**Housekeeping lines stay minimal and plain** (the pre-flight line, the branch line, the confirm line, the pause and end messages, saved-note paths, the database line): no vault folder name the learner was not told about, and no database mention unless a database came up in this session. Explain a command in one plain clause the first time it is mentioned, e.g. *"you can stop and come back later by typing `/pause-work`"*.
Schema reference: `Work/00-How-Work-Tracking-Works.md` under that vault root.

1. Determine the current repo: run `git rev-parse --show-toplevel` from the working directory. If it fails (not a git repo), tell the user and stop — this command only applies inside a repo. Derive `<repo>` as the basename of the toplevel path. Note the *starting* branch and whether the working tree is dirty (`git branch --show-current`, `git status --short`) — you'll cut a fresh working branch in step 6, and the note records that one, not this.

2. Check for a prior session that bears on this one — a **paused** session to resume, or a **completed** session this work follows up on. Look under `Work/<repo>/Sessions/`.
   - **Paused** (a note with `paused_at` set, or a legacy `Work/<repo>/Handoff.md` sidecar): don't resume it inline. Tell the user there's a paused session, summarize its `### What's next` in one line, and point them to `/resume-work`. Ask whether they'd rather resume that (→ stop, they run `/resume-work`) or start a genuinely fresh session anyway (→ continue to step 3; leave the paused note untouched — it's theirs to resume or `/end-work` later).
   - **Follow-up to completed work** — if the user says this continues earlier work that already shipped (its note is `status: completed`): treat it as a **new linked session, never a reopen** (a completed note is a one-time record; its terminal fields are settled and `/end-work` won't reopen it).
     - **Locate the prior note** from the user's description — search `Work/<repo>/Sessions/` on goal text / branch / ticket id / PR number. **Confirm before linking:** state the single best match and confirm it; if several match, list them (`goal`, `started_at`) and ask; if none is locatable or the prior work was never tracked, say so and proceed as a plain unlinked session.
     - Once confirmed, set `continues:` in the new note's frontmatter (step 7) to `<prior session_uid>  [[<prior note path>]]`. The link is **one-directional** — the prior completed note stays **frozen** (not edited). Context flows by *reading* it: read the prior note's `## Lessons` / `## Decisions` / `## Follow-ups` / `## Journal`, on top of the durable facts `/end-work` already pushed to Patterns/Concepts/Learning (surfaced in step 3), as leads for step 5's discovery. Chunks the learner passed in the prior session's `## Lessons` may be recapped instead of re-taught. If the prior note itself carries a `continues:` chain, follow it toward the most-recent relevant ancestor as needed; **never loop** — stop if you revisit a `session_uid`. Cross-repo is not followed (notes live under this repo's `Work/<repo>/`).
     - If this follow-up was **queued** as an open row in the flat `Parking-Lot/INDEX.md` (filter by repo) or a `## Follow-ups` line in the prior note, **close that origin** once the new session note exists — flip the Parking-Lot item's `status` to `resolved` and update its INDEX row, or strike the follow-up line with a pointer to the new session — so it stops re-surfacing in future pre-flights.
   - **Other agents' in-progress notes are not yours to touch:** an `in-progress` note owned by a *different* `agent_id` is left alone — just start your new session. (The ownership match in `/pause-work`/`/end-work` is what keeps concurrent sessions from colliding; a new issue re-arming teach→gate is scoped to *your own* running session, not another's note.)
   - If none of these apply, continue to step 3.

3. Check these vault corners. **Pre-flight receipt (one line, mandatory):** state which corners you checked and the counts — e.g. *"I checked my saved notes from earlier work (N about this project, M open items); nothing in them bears on today's work."* Name a notes folder only if a heads-up needs it, and then say in a few words what it holds; everything else on the line, and every heads-up, passes the term check (step 8). Then surface only hits that bear on this session ("heads up, from a prior session: ..."). After the goal is known (step 4), explicitly check whether any **open** Parking-Lot entry for this repo touches the goal area and flag it if so — do not force irrelevant mentions.
   - `Agent/Feedback.md`: standing behavioral rules (git/PR/CI/web3/vault workflow) that fire on specific actions. Not repo-scoped; read it every session so the action-triggered rules are in hand before any git/PR/web3 work. (Always-on rules like writing style and edit scope live in AGENT.md and are already loaded.)
   - `Agent/Patterns/<repo>/` (see `Agent/README.md`) — durable facts about how this codebase behaves. Also read here (alongside `Concepts/`/`Modules/`/`Learning/`) before CCC Phase B discovery, as leads to check against the code. A vault note is never a fact until the code confirms it. If the code contradicts a vault note, add a `## Follow-ups` line marked **Stale** (the note, what the code says instead); `/end-work` step 5 corrects it.
   - `Parking-Lot/INDEX.md` (see `Parking-Lot/README.md`) — filter by repo; read the flat index, then open item files under `Parking-Lot/<repo>/` as needed. Real issues noticed in passing and deferred, not yet fixed. Distinct from `Agent/Patterns/`: don't conflate the two when reading or later writing to either. If a fix for one ships during the session, flip that item's `status` to `resolved` in the item file **and** update its INDEX row rather than leaving it stale. Also read `Parking-Lot/` (filtered by repo) as leads before CCC Phase B discovery.

4. **Restate the ask and set the goal, before touching anything.** Take the ask from `$ARGUMENTS` or the user; if there is none, ask in one line what this session is for (one question, move on). Restate it in plain terms so both people are aligned: for a bug, what is wrong; for a change, what the ticket is trying to solve; for a PR review, "review PR #<n>". The restated ask is the session goal. Then say in one line that teaching comes first, e.g. *"I'll explain how this works today before anything is edited (say 'just fix it' to skip)."* Both lines are learner-facing and come before any chunk is taught, so they pass the term check (step 8) with only everyday words and terms they define themselves: no code words, no service or system names the learner has not been told about, and no internal words (CCC §2e).

5. **Build the picture curriculum (CCC Phases A→F, reading only).** Cite and obey Code Concept Curriculum. The picture is how the relevant code works today and why the goal exists, from the root up: for a bug, the root cause from first principles; for a change, the current state of affairs and its surrounding context; for a PR review, in this order — the state of affairs before the PR, the problem the PR attempts to fix, and what the PR does. Run **Phases A→F** (graph and chunks) until `discovery_status: clear`, or escalate per the twins (present the failing checklist rows; do not invent facts).
   - **Size the curriculum to the change.** A one-line rename gets a one- or two-chunk graph and one question, never a manufactured lesson. A deep bug gets as many chunks as the code forces. This is proportionality, not a bypass.
   - **The graph is an internal record, not the lesson.** Do not show the learner the graph, the chunk list, the discovery checklist, or a claims table. Teaching happens in step 8, one chunk of prose at a time.
   - **State of affairs outside the diff or the edit**, required when correctness depends on something outside it (config, a service boundary, or a contract or value consumed by another service or repo): look beyond it before judging. Is the runtime or a consumer in another repo, is there a companion or sibling PR on the same ticket, does deploy ordering matter. When the goal is a PR review, this look belongs to the first item (the state before the PR).
   - **Live before-state (when the goal changes an existing user-visible surface):** observe that before-state live in a running app (read-only setup is fine) before any source edits. Skip for greenfield work with no existing surface to observe.
   - **Read-only** here: reading, grepping, and running tests is fine; writing is not. Persistence is `/end-work`'s job, and `/pause-work` saves the chunk list.

   **Hard gate on edits (every session):**
   - **Gated:** editing source-controlled files, and state-mutating git operations (commit/checkout/reset/stash) other than step 6's branch cut. None happen until explicit go-ahead, even if the change seems obvious or small.
   - **Taught-first precondition (the enforcement backstop):** go-ahead to edit a fix for an issue is **blocked until that issue's picture chunks and solution chunks were taught and passed** (Gates 1 and 2, step 8), with `discovery_status: clear`. Teaching therefore can't be skipped — the fix needs an edit, and the edit is gated on the teaching — rather than relying on remembering to teach. The only bypass is the per-item escape hatch below.
   - **Not gated:** reading code, grepping, running tests, installing deps, starting/restarting servers, read-only git. The investigation needed to describe the issue and build the curriculum is always fine.
   - **"Explicit go-ahead" means:** an affirmative directive ("go ahead," "do it," "fix it," or an escape phrase) that names or unambiguously references a specific proposal already on the table. Scoped only to the exact diff discussed — an adjacent "obviously needed" change (a nearby rename) needs its own separate go-ahead. Naming a fix-applying skill directly (`/code-review --fix`, `simplify`) counts as go-ahead for that skill's own scope.
   - **Escape hatch:** the user saying "just fix it" / "just build it" / "skip the loop" (or, for a review, "just the bottom line" / "just the verdict"), up front or mid-loop, exits the teaching *and* counts as go-ahead for that specific change. It is a per-instance bypass, not a standing override, and you never skip the teaching on your own read of what's "trivial" — a trivial change gets a tiny curriculum, not none.

6. **Set up the working branch (mandatory git-flow — do this before creating the session note, so the note records the branch work actually happens on).** Runs for every fresh session, with two exceptions: the user chose in step 2 to resume a paused session (that's `/resume-work`'s job), or the goal changes no code in this repo (reviewing someone else's PR or diff) — then leave the checkout on its current branch, never switch a shared checkout just to review, and skip straight to step 7.
   a. **Pick the base branch:** prefer `develop`; if the repo has no `develop`, use `main` (or `master`); if it has none of these, ask the user which branch to base off. Check with `git branch --list develop main master` and `git branch -r`.
   b. **Switch to the base and pull it fresh:** `git checkout <base>` then `git pull`. **Leave any uncommitted local changes exactly where they are** — do NOT stash, commit, or discard them; git carries them across the checkout. If the checkout is blocked because local changes would be overwritten, **stop and tell the user** — never force it or throw away their work.
   c. **Cut the new branch off the fresh base:** `git checkout -b <new-branch>`. Any uncommitted changes ride along onto the new branch — that is intended ("leave them where they are").
   d. **Name the branch by the repo's documented convention, never an ad-hoc guess.** Read `Agent/Patterns/<repo>/git-branch-and-commit-conventions.md` (already surfaced in step 3) and follow it exactly. For `vivenu-core`: `AFG-####/kebab-case-slug` for `AFG-` tickets (ticket ID as the prefix, slash, no `feature/` wrapper), and `feature/<ticket-id-lowercase>-<slug>` for other prefixes (`TBT-`, `SPX-`, ...). Derive the slug from the goal. Get the ticket ID from the goal / `$ARGUMENTS` if present; if there is no ticket, use the **ticketless rule** in that conventions file (`<type>/<kebab-slug>` — do not ask for a ticket that does not exist). If the repo has no conventions file, **ask the user for the naming pattern** rather than inventing one.
   e. Use this new branch as `<branch>` in the session note below, and confirm the switch to the user in one plain, term-checked line, e.g. *"I got the latest shared copy and made a separate working copy, called a branch: `<name>`."*

7. Create `Work/<repo>/Sessions/<YYYY-MM-DD-HHmm>-<slug>.md` (slug derived from the goal, kebab-case, short) with:
   ```yaml
   ---
   repo: <repo>
   branch: <the new branch created in step 6>
   started_at: <timestamp>
   ended_at:
   status: in-progress
   session_uid: <stable unique id for this session, generated once here with `uuidgen` and never changed — agent-agnostic, survives every handoff>
   agent_id: <the current harness's session identifier, or blank if it exposes none>
   goal: <goal>
   db_baseline: none   # none | captured | restored — the local dev-DB snapshot lifecycle (see step 8's DB Baseline Protocol and /end-work's restore step)
   continues:          # optional — set ONLY on a follow-up session: <prior session_uid>  [[prior note path]]. One-directional; the prior completed note stays frozen (see step 2). Omit otherwise.
   ---
   ```
   When no branch was cut (step 6's no-code exception), set `branch:` to the checkout's current branch with a `(read-only, no branch cut)` note, and keep the PR under review in `goal:`. **Note invariant:** this note is created for every session, unconditionally, before any teaching or gating below — the record is mandatory; only the teaching is ever skippable.

   These are **two different id fields with two different jobs — do not conflate them**:
   - `session_uid` is the note's **stable identity**. Generate it **once, here, at note creation** — run `uuidgen` and paste the value — and then **never change it again**: not on pause, not on resume, not when a different agent takes over. It is what uniquely names *this work session* regardless of which agent is driving now or drove earlier. It's generated the identical way for every agent, so it is fully agent-agnostic and not tied to any one tool's environment variable. If `uuidgen` is somehow unavailable, fall back to any unique token (e.g. the note's `<YYYY-MM-DD-HHmm>-<slug>`), but prefer a real UUID.
   - `agent_id` identifies the agent session that **currently owns** the note — the one running right now. Each agent stamps the session identifier exposed by its current harness. This is the field `/pause-work` and `/end-work` **match on** to act on *this* agent session rather than whichever in-progress note is newest, and it is **re-stamped on every `/resume-work`** because resume runs in a new agent session. If the harness exposes no session identifier, leave `agent_id` blank and note it to the user — `session_uid` still uniquely identifies the session.
   Sections: `## Goal` (filled), `## Lessons` (empty — the teaching record; see the Lessons rule in step 8), `## Pedagogy` (empty — the teaching checkpoint; format below), `## Journal` (empty — the running capture; see the Journal Protocol in `Work/00-How-Work-Tracking-Works.md`), `## Log` (empty), `## Files Touched` (empty), `## Decisions` (empty), `## Follow-ups` (empty), `## DB Baseline` (empty — the local dev-DB snapshot record; see the DB Baseline Protocol at the end of step 8).

   **`## Pedagogy` (the teaching checkpoint, internal record).** Created empty with the note and written live from the start: add an item's row when its teaching starts, and update `chunks:`, `passed_chunks:`, the gate fields and `claims:` as they change. It is never part of `## Handoff`, and `/pause-work` refreshes it in place. One row per work item (one session can teach more than one issue; see the new-issue fork):
   ```
   - item: <short id/desc> | gate1: passed|open | gate2: passed|open|n/a | pos: step N of M|not-started|n/a | status: active|done|opted-out|parked
     chunks: <id> (picture|solution; after <pred ids or ->)[; stuck-added]: <one-line claim>; ...
     passed_chunks: <id>, <id>, ...
     claims: G1: <learner answer>; <learner answer> | G2: <answers or empty>
     discovery_status: pending|clear|escalated
     convergence_status: pending|converged|escalated
     adversary_status: pending|clear
     stuck_revisits: picture <N>, solution <N>
   ```
   The pipe fields are the authority for passed/open. `stuck_revisits:` counts the stuck revisits used so far in each teach run (CCC H7: one each for the picture and the solution); bump it when CCC Phase H runs, and never reset it on pause or resume. `gate2: n/a` and `pos: n/a` when the goal changes no code in this repo (a review). `passed_chunks:` gets each chunk id as soon as it passes, picture or solution. This row is for agents: its ids, claims and fields are never read out to the learner.

8. Confirm to the user in one plain line: the goal and where this session's notes are saved (e.g. *"I'll keep notes on this session in `<note path>`."*), term-checked like everything else; the branch was already said in step 6e. Then run **the comprehension-gated tutorial** — the same flow for every session, no escape phrase used. Phases 1–3 are read-only (reading/grepping/running tests is fine; no source edits, no state-mutating git). Editing begins only in Phase 4.

   **How every piece of teaching is delivered (CCC Phase G).** One chunk per turn: short full prose, root chunks first, then exactly one plain question (the chunk's use-check), then wait for the answer. Tables, lists, the graph, and the claims are never the teaching. When more than one chunk is ready, serve the next one in graph order without asking; change the order only if the learner asks (CCC pick rule X). **Term check before anything is shown (CCC G2f, the Math Academy rule — no term appears out of nowhere):** it covers **every learner-facing line** (defined at the top): the restated goal, pre-flight and confirm lines, every chunk, its question, any hint or corrective prompt, a chunk Phase H adds, every solution chunk, the resume recap and "what's next" line, the Phase 4 walkthrough, and the end-work message. Every term must be an everyday word, or defined in that same text, or defined in a chunk the learner already passed. Code words (test, loop, catch, function, request and the like) are not everyday words: use one only once it is defined. Run the layman-terms denylist pass on the text and replace each hit with its plain equivalent. Then run the **internal-word denylist** (CCC §2e): chunk, node, graph, gate, claim, hold, phase, use-check, ready set, and chunk or fact ids like P1 or S3 never appear in learner-facing text — use the plain replacement (e.g. "the part about <what it taught>" instead of "P2"). **Names are exempt only as names:** a file path cited as `<repo>/<path>:line`, a branch name, a note file name, a vault folder name, or a command name (e.g. `/resume-work`) is a name, not a term, but only when shown as a name in code formatting. Jargon inside a name is not taught by it: if the text uses a word from the name as a word, that word must pass on its own. A technical term that has to stay gets an inline definition of a few words. If a term still fails, the text is blocked: define the term inline, or add a prerequisite chunk and teach it first. Never show a blocked text. **Also before anything is shown (CCC G2g, G2h):** no paragraph over about 90 words and at most 3 new terms defined per paragraph; a question names every quantity it asks about (a total, a count, a time), and the chunk taught that quantity before the question; and every line number, count or list size is checked against the actual file or test output (a mismatch blocks the text, e.g. "six tests" with five listed).

   **Hints and stuck.** A wrong answer gets the chunk's corrective prompt: a plain hint that names the specific missing piece, never cryptic, never the answer, and no hint before the first attempt. **When the learner is stuck (CCC G6):** they say they are stuck or don't know, **or** they answer wrong two times after the plain hint (a wrong answer after the hint gets the hint again in more direct words; the second wrong answer after the hint is stuck). **Stuck = a missing prerequisite (CCC Phase H):** do not repeat the same chunk in other words. Say in one line that a piece is missing, add its prerequisite node and chunk, teach that chunk (term-checked like any other), then re-ask the chunk where the learner got stuck. **Re-ask = repeat its question only**, word for word, without showing its explanation again. The wrong-answer count for that chunk does not reset.

   **Lessons rule (the teaching record).** Each time a chunk passes, append it to the note's `## Lessons` section, word for word:
   ```
   ### <short plain headline>[ — added because you were stuck][ — taught again] <!-- <chunk id> -->
   <the chunk's prose exactly as shown>
   **Question:** <the question exactly as asked>
   **Your answer:** <the learner's passing answer, verbatim>
   ```
   **The learner rereads `## Lessons`, so its visible text is learner-facing.** The heading shows only the plain headline and the plain-word markers; the chunk id sits in the trailing HTML comment `<!-- <chunk id> -->` on the heading line, hidden when the note is rendered. That comment is the link to `passed_chunks:` in `## Pedagogy`. Run the term check, including the internal-word pass (CCC §2e), on the headline and markers before writing them; the prose and question were already checked when shown and are copied exactly. A chunk that Phase H added carries the `— added because you were stuck` marker. Solution chunks are recorded the same way. **Taught again:** when CCC H5 drops a pass and the chunk is taught again, its new pass is a **new** entry with ` — taught again` after the headline (before the comment); the old entry stays exactly as it was. The section is append-only: never paraphrase, summarize, rewrite, or remove an entry after the fact; `/pause-work`, `/resume-work` and `/end-work` leave the section as it is.

     - **Phase 1a — Teach the picture (CCC Phase G).** Step 5 already ran CCC A→F. If `discovery_status` is `pending` or `escalated`, finish or escalate CCC first, and never teach on an unclear graph. Then serve picture chunks from the ready set as described above until every picture chunk has passed. **Resume:** see `resume-work.md` — recap passed chunks, then continue at the first unpassed chunk in the saved `chunks:` list.
     - **Phase 1b — Gate 1 = every picture chunk passed (CCC Phase I).** Gate 1 is not a separate quiz after the teaching. It passes when every picture chunk has a use-check pass (including chunks Phase H added) and every named hold is resolved, with `discovery_status: clear`. **Never advance without a pass, never write code as a fallback;** fatigue → offer `/pause-work`. **On pass:** make sure `passed_chunks:` holds every picture chunk id and write `claims: G1: <the learner's passing answers, one per chunk>` on the item's row in `## Pedagogy` (grammar tidy OK; **content rewrite forbidden**; agent-authored answers forbidden), then `gate1: passed`. **Block `gate1: passed` while `discovery_status` ≠ `clear`.** See step 7 for the row.
     - **Phase 2 — Teach the intended solution (same graph, delta only; CCC Phase S).** Still read-only; still **no language snippets**. Add solution nodes on top of the picture graph per the CCC solution extension (Phase S in the twins). Each solution node cites the picture fact ids it builds on plus the ticket. The passed picture chunks are the floor, so do not re-teach them and do not re-run CCC A→E when `discovery_status` is already `clear`. Rejected alternatives stay one line each. An empty delta is legal ("no new pieces; the fix is one step on what you already know"). **If the solution needs code facts the picture graph does not hold, re-enter CCC Phase B** and do not continue until `discovery_status` is `clear` again, or escalate. Then serve the solution chunks exactly as Phase 1a, with no recap first (this is not a resume). **Stuck during the solution chunks (CCC H8):** it stays under Gate 2 and never reopens Gate 1; picture passes stay. A missing code fact goes back to CCC Phase B and is added as a stuck-added chunk recorded under the solution. A gap in reasoning rather than a code fact (e.g. why waiting before a new try helps) is added as a solution-side prerequisite chunk, also under the solution. The solution is its own teach run with its own one stuck revisit (CCC H7). When the goal changes no code in this repo (a PR review), the solution chunks are the verdict's reasoning: what the PR gets right and what it gets wrong, each tied to the picture.
     - **Phase 3 — Gate 2 = every solution chunk passed (CCC Phase I on the delta).** Same rule as Phase 1b on the solution chunks. **On pass:** make sure `passed_chunks:` holds every solution chunk id (including stuck-added solution chunks) and append `G2: <learner answers>` to the same `claims:` sibling (do not rewrite G1), then `gate2: passed`. Do not record `gate2: passed` while a Phase B rediscovery for this item is still `pending` or `escalated`. For a PR review, Gate 2 is followed by the verdict, and there is no Phase 4. Posting comments, approving, or requesting changes is publishing, so confirm the exact text with the user before posting.
     - **Phase 4 — Tutorial walkthrough (real code begins).** The learner is now editing real code. Say so in one line as Phase 4 opens: every step opens with why it goes there, and for each step they choose whether to type the change themselves or have you type it, and can switch at any step (e.g. *"Now we make the real change, one step at a time. For each step, you can type it yourself or ask me to type it, and you can switch whenever you like."*). **Then define the code words first:** before the walkthrough uses any code word the lessons did not teach (e.g. test, loop, catch, function), define each in one short plain sentence; define only the few the walkthrough needs. Always include, once, what a file is, what a test is and what "the tests pass" means (every check in them gave the expected result), and how to read a code location (e.g. *"`client.ts:14` means line 14 of the file `client.ts`"*). Show at most 2 code locations per paragraph. Then tie what each passed chunk taught to the code it lives in, naming the chunk by its plain headline (never its id), citing the code as `<repo>/<path>:line` in visible prose (a Cursor widget header does not count as the cite). Then decompose into ordered edit steps; do one at a time and do not advance to step N+1 until step N is finished. **Reaching Phase 4 (Gate 2 passed) *is* the go-ahead** for the agreed solution — the user drives the edits, so no separate "go ahead?" is needed. For **each step**:
       - **Lead with the why-here:** open the step with *why this file* and *why this edit here* before any mechanics — proportionate to how non-obvious the choice is (one clause for a self-evident step, the full reason for a load-bearing one). Tie back to a passed chunk by its plain headline (e.g. "as we saw in the part about <its headline>, ..."), never by its id. Cite the file by `<repo>/<path>:line` in visible prose (Cursor widget headers do not count). This holds for **every** step, simple or not — the user never applies an edit without knowing why it goes there.
       - **The learner chooses who types each edit.** The solution is already agreed (Gate 2). For each step the learner either types the change into the file themselves, or asks you to type it (describing it in plain words or simply saying "you type it"). They can switch at any step; never choose for them, and ask in one plain line only when they have not said. **They type it:** you verify and correct; you may write complementary tests/fixtures/scaffolding. **You type it:** type only what this step of the agreed solution says (don't widen it, and don't route the fix logic through a "helper" or test), then replay it.
      - **Replay, not a diff (only when you typed the change).** Never dump the diff. Replay the change against the agreed solution, step by step. For each step: one plain sentence that names the lesson it applies, by its plain headline (e.g. *"Step 1: this is where the comma rides along, so we cut it off here."*), then the 2–3 key lines that do it, as code, with their location as `<repo>/<path>:line` (at most 2 locations per paragraph). Everything else (imports, renames, formatting) is one line: *"Plus small supporting edits in `<file>`."* Show every changed line only if the learner asks. The sentences pass the term check and the internal-word denylist like any other learner-facing text, and every line number is checked against the file (CCC G2h). **The replay ends your turn** with exactly this question, as its last line: *"Does this match what we agreed?"* Then stop and wait. Do not run the tests or say "Done" in the same message as the replay. If the learner corrects it, apply the correction, replay what changed, and end the turn with the same question again. When the learner typed the change themselves, there is no replay and no question; verify it instead.
      - **Replay, learner's answer, then tests, then "Done".** Run the tests only after the step's change is in the file and, if you typed it, the learner has answered the replay question with a yes (or with corrections that you applied and replayed, and they then said yes). Report the result with counts checked against the real output. Say "Done" only after the tests pass, in one plain line that names what the code now does (e.g. *"All eight tests pass. Done: the code now waits before each new try."*), so "Done" always means checked and agreed. If the tests fail, say so plainly, never say "Done", and fix the step with the learner first (the stuck rules below apply).
      - **"Just fix it" during Phase 4** means you type the rest of the agreed change with no replay and no replay question, so there is no wait. The tests still run, and "Done" still waits for them to pass.
       - For a step you judge *simple*, still lead with the brief why-here, then ask the user to attempt it; for a non-trivial step, give the fuller why + approach, then the user implements. Everything you write here passes the same term check as a chunk.
       - **Stuck on a step** (same trigger as above): if the gap is a concept, run CCC Phase H under the solution, as in Phase 2 (add the missing prerequisite chunk, teach it, record it in `## Lessons` as added because you were stuck and in `## Pedagogy` under the solution, then resume the step). Otherwise give a plain hint that names the specific missing thing — never cryptic, no hint before the first attempt, and never paste the fix pre-emptively. When the learner is stuck on the step by the same trigger as CCC G6 (they say so or don't know, or two wrong attempts after the plain hint) and the gap is not a concept, reveal and explain; then the learner types it or asks you to (with the replay), then the tests, then "Done". Terminal states: the step gets done, or the session pauses; never a silent skip.
   - **Escape hatch (sole bypass):** the user saying "just fix it" / "just build it" / "skip the loop" (or "just the verdict" for a review), up front or mid-loop, exits the whole sequence and counts as go-ahead for that specific change. Said during Phase 4, it skips the replay and its question but not the tests: "Done" still waits for them to pass. Never silently skip the tutorial on your own read of "too trivial": the answer for a mechanical change is *proportionality* (a one- or two-chunk curriculum), not omission.
   - **Nothing teachable** (e.g. a pure config/data edit with no mechanism to understand): one chunk that states the one-clause why with its one question, then the Phase 4 edit. Don't manufacture a lesson. This is proportionality at its floor, **not** a second bypass; the escape hatch above remains the only bypass.

**DB Baseline Protocol (local dev-DB snapshot + restore).** During the work you may change the **local** dev DB purely to exercise the change — seed a user/org, insert a fixture, flip a feature-flag row, backdate a record.    - **Disposable-local guard (required).** Snapshot only a genuinely **local, disposable** dev DB. If the target is shared/staging/remote, do **not** snapshot or plan a restore — tell the user and skip (`db_baseline` stays `none`); restoring shared infra would destroy other people's data.
