# New Session

Vault root: `/Users/nlekanetamba/Documents/DigitalBrain`. Scope: whichever onboarding curriculum applies for this request — see `Vivenu/Track-State.md` for the two tracks (`web3` → `Vivenu/Onboarding-Web3/`, module prefix `W`; `checkout` → `Vivenu/Onboarding/`, module prefix `M`) and how routing works. This is the same procedure as saying "start W01" or "start M01" in plain conversation, per each track's own `Engine/00-How-This-Works.md` — invoking it explicitly or just asking in plain language both route here.

## Step 0 — resolve which track this session is on

- **`Vivenu/Track-State.md` is missing, its frontmatter doesn't parse, or `current-track` names a track not in its Tracks table:** don't guess — ask which track applies before doing anything else in this step.
- **`$ARGUMENTS` says "switch"/"change the active track" explicitly** (e.g. "switch to checkout track," "make web3 active"): this is not a one-off — run `/switch-track`'s own logic to durably update `current-track`, then proceed with the newly-active track. This is the *only* phrasing (besides the literal `/switch-track` command) that persists — see `Vivenu/Track-State.md`'s "What actually persists vs. what's a one-off, precisely" for why this exact line is drawn where it is.
- **`$ARGUMENTS` names a track-prefixed module** (e.g. "start W03", "quiz me on M07"): that prefix picks the curriculum root for this one session, regardless of `current-track`. This is a one-off override — it does not change `Vivenu/Track-State.md`. Say so explicitly if it differs from the active track ("that's a checkout-track module — teaching it now, but the active track stays web3").
- **`$ARGUMENTS` names a bare module number with no letter prefix** ("start 03," "quiz me on 3"): don't guess which track it belongs to — ask. This is deliberately not resolved via `current-track`, since the entire point of prefixing module IDs was to make a module reference unambiguous; silently falling back to `current-track` here would defeat that.
- **`$ARGUMENTS` is empty, or names an intent with no module ID** ("quiz me", "continue", nothing): use whichever track `Vivenu/Track-State.md`'s `current-track` names.
- **`$ARGUMENTS` names a track by word without saying "switch"** ("start the next web3 module", "quiz me on checkout"): honor that track for this request, same one-off-override treatment as the prefixed case above — it does not change `current-track`.

If `$ARGUMENTS` names one track by word/prefix and separately mentions the *other* track's name in the same request (e.g. "quiz me on the web3 M03 material," which names checkout's M03 but says "web3"): the module prefix wins — a prefixed module ID is the more specific signal. Say which track you resolved to and why, so a genuine mix-up gets caught immediately rather than silently taught on the wrong track.

Everything below refers to "the resolved track" — its `Curriculum-Map.md`, `Progress-Dashboard.md`, and `Modules/` folder.

## Steps

1. Read the resolved track's `Progress-Dashboard.md` for any module overdue on `next_review`. Separately, for any module whose `status` is `learning`, check that Module note's own **Session Notes** section for unresumed state, and note its `last_jit_touch` field if present (written by `/learn` — see `{{AGENT_COMMANDS_DIR}}/learn.md`) so a resumed session can mention it too, not just a fresh start. **Also** — regardless of which track was resolved — read the *other* track's `Progress-Dashboard.md` and check whether it has any module more than 7 days past `next_review`. If so, surface a one-line nudge before proceeding (e.g. "checkout's M02 review is 9 days overdue — still want to stay on web3 today?") per `Vivenu/Track-State.md`'s staleness guard — this is a nudge, not a gate, so continue with the resolved track's session either way unless the user redirects. Also scan `Learning/` (sibling to `Vivenu/`, see `Learning/README.md`) for any note past its own `next_review` — same nudge-not-gate treatment, surfaced alongside the checks above. **Also** read `Work/Owed-Learning.md` (deferred work-lessons written by `/end-work` — see `{{AGENT_COMMANDS_DIR}}/end-work.md`) and surface any owed lesson as a one-line nudge ("deferred lesson from {source_session} — take it now, or study the track?"), same nudge-not-gate treatment. These carry no `next_review` — they're owed until taken, not spaced-rep scheduled, so the staleness math doesn't apply to them; the file's mere non-emptiness is the trigger.
2. If `$ARGUMENTS` names a specific module or intent: verify the module exists in the resolved track's `Curriculum-Map.md` and its prerequisites are `practicing` or `mastered`. If either check fails, say so and ask how to proceed rather than starting anyway. If both pass, honor the request — skip to step 4.
3. No argument given: if step 1 found a checkpointed or overdue module on the resolved track, surface it and ask whether to resume/review that or do something else. If nothing's checkpointed or overdue, name the next natural module per the resolved track's `Curriculum-Map.md` and ask if that's the plan for this session. **Even when an explicit argument in step 2 pointed elsewhere,** if step 1 found something overdue or checkpointed on the resolved track's *own* dashboard on a different module, mention it briefly before proceeding.
4. Determine session type from what's being asked. **Teaching and quizzing here run under the [Teaching Standard (`Teaching-Standard.md`): plain + first-principles (TS-1); cite files/notes by `repo/path` or vault-relative path (TS-2); hints and questions plain, never cryptic (TS-4) — a Module Hat's Socratic style is fine as long as each question plainly states what it's probing].** TS-3 and TS-5 do **not** apply (this is study, not editing production code), and TS-6's ungraded pass-or-pause ladder does **not** govern the graded curriculum quizzes below — those keep their own mastery mechanic per the Module Hat.
   - **New teaching** ("start W0X"/"M0X") — read that Module note in full (Learning Objectives, Key Files, prerequisites already satisfied per the Curriculum Map) before teaching anything. If its frontmatter has a `last_jit_touch` date (written by `/learn` — see `{{AGENT_COMMANDS_DIR}}/learn.md`), mention it before teaching (e.g. "this was JIT-touched on {date} for a specific task — teaching the full module now") rather than treating it as wholly untouched.
   - **Resume** ("continue W0X"/"M0X") — read that Module's Session Notes first and resume from the stated point, per that track's `Engine/00-How-This-Works.md`. Also check for a same-day `Lessons/` note already marked `in-progress` for this module.
   - **Quiz/review** ("quiz me on W0X"/"M0X", or "quiz me, interleaved") — retrieval practice only, no re-teaching, per the relevant Module's Hat. An interleaved quiz stays within the resolved track unless explicitly asked to mix both.
   - **Take an owed work-lesson** ("take the owed lesson", or accepting the step-1 owed-lesson nudge) — teach the deferred lesson named in `Work/Owed-Learning.md`. Build it from what *survives* at pickup time: the `source_session` note's `## Journal` **plus** the durable notes `/end-work` persisted for that session (its `Concepts/`/`Learning/`/`Agent/Patterns` entries) — **not** live git state or the original conversation, both of which are gone by now. This is off-track side-teaching, **not** curriculum advancement: touch no module frontmatter (`next_review`/`status`/`last_reviewed`/`ease`) and no `Progress-Dashboard.md`, and `/end-session` must not try to progress a module for it. When the lesson lands, **clear it**: remove its row from `Work/Owed-Learning.md` and set `lesson: done` on the `source_session` note (leave that note's `status: completed` untouched — only `lesson:` flips).
   - **Doesn't match any of the above** — don't force it into one of the buckets above. State your interpretation and confirm before proceeding.
5. Before teaching anything that references real `vivenu-core` file paths, check the resolved track's `Curriculum-Map.md`'s `last_synced_at` against the staleness policy in that track's `Engine/Sync-Core.md`. If it looks stale, say so and offer to run `/sync-core` first.
6. Proceed with the session. End it with `/end-session` — either of you can invoke it; Claude doesn't run it unprompted.
