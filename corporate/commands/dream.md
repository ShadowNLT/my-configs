# Dream

A maintenance ritual, not a work session. The goal mirrors what sleep-driven memory consolidation does biologically: strengthen what's still true, prune what's gone stale, connect facts captured separately but related, and surface insights only visible when looking across everything at once rather than one file at a time.

## Scope
`{{AGENT_HARNESS_MEMORY}}/.../memory/` (harness memory), `{{VAULT_AGENT_DIR}}/Patterns/`, `{{KNOWLEDGE_VAULT_ROOT}}/Work/*/Sessions/`, every `{{KNOWLEDGE_VAULT_ROOT}}/Vivenu/Onboarding*/` sibling (see that vault's track-state file for the full list, and treat any future sibling the same way without needing this file updated first), and `{{KNOWLEDGE_VAULT_ROOT}}/Learning/` (freestanding notes written by `/learn` — see `Learning/README.md`). `Lessons/` and `Concepts/` inside each `Onboarding*/` sibling, and `Learning/` itself, get exactly one exception to the propose-only default below — auto-fixing broken links — nothing more.

## Short-circuit
Before doing anything else, check whether anything's actually changed since the last `Agent/Dreams/*.md` entry (new session notes, new/updated patterns, memory edits). If nothing's new, say so in one line and stop — don't run a full pass for no material.

## Process
1. **Consolidate harness memory** — merge duplicate entries, fix now-stale facts, prune superseded ones, tighten the index. This is the same job as the built-in `consolidate-memory` skill; invoke it for this step if available rather than reimplementing it.
2. **Re-verify patterns** in `Agent/Patterns/<repo>/`, especially stale `verified_last` dates — grep the real repo for the referenced file/class/behavior.
   - Confirmed → bump `verified_last` freely, no confirmation needed.
   - Drifted → **propose** the correction to the user rather than silently rewriting the Fact; a wrong technical claim written here doesn't stay contained, it resurfaces later via `/start-work`'s callouts.
3. **Mine session logs** in `Work/<repo>/Sessions/` for recurring unresolved follow-ups, or a theme spanning multiple sessions that hasn't become a pattern yet.
4. **Check onboarding health, per sibling** — read each `Onboarding*/Progress-Dashboard.md` for modules overdue on `next_review`, or stalled mid-module (old, unresolved Session Notes). Flag only — never write onboarding frontmatter yourself; `next_review`/`last_reviewed` mean an actual teaching/quiz interaction happened, which a dream pass isn't. Note each `Curriculum-Map.md`'s `last_synced_at` too — if `/sync-core` ran very recently for that track, treat any Concept/Module content touching what it just verified with a bit more skepticism than usual. Also glance at `Vivenu/Track-State.md`: if the inactive track is well past the 7-day staleness-guard threshold `/new-session` already nudges about, that's worth surfacing as an insight (step 6) if it's been going on long enough to look like a pattern rather than a normal short gap — don't duplicate `/new-session`'s own nudge for an ordinary few days overdue.
   - **Hats.md drift check:** if more than one `Onboarding*/Engine/Hats.md` exists, diff them. The four persona definitions and their core instructions are meant to match across siblings by design (only illustrative examples are expected to differ, adapted per domain) — surface anything beyond that as a proposal, since nothing else in this system ever checks these files against each other.
5. **Connect** — add missing `[[wikilinks]]` between facts captured separately that actually relate (a pattern that should reference an onboarding module, a session follow-up that's really an existing pattern).
   - **In `Concepts/` specifically:** scan for broken wikilinks — a `[[link]]` whose target note doesn't exist in the vault — and fix those directly, no confirmation needed (this is the one auto-apply action in this folder pair). Separately, surface (don't create or merge yourself) two more patterns as proposals: two Concept notes that look like they describe the same entity, and an entity mentioned across multiple `Lessons/` notes that never got its own Concept note. **If a sibling's `Concepts/` or `Lessons/` folder doesn't exist yet** (no taught session has happened on that track yet), skip it for that sibling — nothing to scan, not an error, same as `/sync-core` skipping a Module note with no "Key Files" section.
   - **In `Learning/`:** same broken-link auto-fix as `Concepts/`. Separately, surface (don't merge yourself) any two notes that look like they describe the same topic under different slugs — `/learn`'s own filename-matching check is a weaker signal than an actual read, so this pass is the real backstop against near-duplicates slipping through. If `Learning/` doesn't exist yet (no `/learn` invocation has ever persisted anything), skip it — not an error.
6. **Surface insights** — what's true in aggregate that isn't visible from any single file (a recurring struggle area, a cadence that's drifted, scope creep, a contradiction between two memories)? State the evidence basis inline ("based on 3 sessions," not asserted as settled fact) so it's calibrated, not just confident-sounding. Only report a real one — don't manufacture an insight to have something to say.

## What to just do vs. what to propose
- **Do freely, no confirmation needed:** housekeeping inside `Agent/` — merging exact duplicates, fixing links, bumping `verified_last` on a confirmed pattern. The one equivalent inside any `Onboarding*/Lessons/`, `Onboarding*/Concepts/` (either sibling), or `Learning/` is fixing a broken `[[link]]` — a link whose target note doesn't exist. That's it; nothing else in these folders is auto-apply (see below for why).
- **Propose, don't apply:** rewriting a pattern's stated Fact (even though it's inside `Agent/` — wrong facts propagate back out); merging two Concept notes, or two `Learning/` notes, even when they look like duplicates (present what each note would keep or lose in the merge and let the user decide — a "clear" duplicate can still be two facets of the same entity the user deliberately kept separate); tightening a Concept note's or `Learning/` note's wording (either one's body *is* a distilled piece of what was taught, so any wording edit is indistinguishable from rewriting the teaching record — same rule as Lessons, just phrased differently); rewriting what a Lesson note says was actually taught, or restructuring the Concepts taxonomy (that's the user's learning record, not the agent's to silently revise); a Concept note's `verified_last`/`introduced_in` frontmatter, or a `Learning/` note's spaced-rep frontmatter (`next_review`/`interval_days`/`ease`) — these follow the same discipline as `Agent/Patterns/`'s `verified_last`: bump only via the real mechanism that owns them (a real teaching interaction, or `/learn` itself), never as a side effect of a dream pass; changing `Vivenu/Track-State.md`'s `current-track` (that's `/switch-track`'s job); and anything else in `Work/`, any `Vivenu/Onboarding*/`, `Learning/`, or harness memory that represents the user's own facts/decisions rather than the agent's own housekeeping.

## Output
Write `Agent/Dreams/<date>.md`: what was reviewed, what changed, any insight surfaced (with its evidence basis), and anything proposed for the user's review. A dream that found nothing gets a two-line entry, not padding.
