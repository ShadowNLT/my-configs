# Update Writing Rule

Triggered when the user flags an assistant output, usually the most recent one, as not meeting the bar: too AI, stilted, hedging strangely, or otherwise something they're not proud of. It can also be triggered automatically when `apply-writing-rule` hands off a resolved iteration trail instead of a single reply, see step 1 for how the two input shapes differ. The point of this command is that passing the current rules doesn't mean the rules are complete. Use the actual failure as a chance to find what they don't cover yet.

1. **Identify the target text.** Default to the assistant's most recent substantive reply in this conversation. If `$ARGUMENTS` points at something else, a pasted excerpt, an earlier message, a PR comment, use that instead. If the input is explicitly labeled as a trail (`apply-writing-rule` marks it this way when it hands off: an original, a sequence of rejected drafts each paired with the feedback that killed it, tags marking any technical/factual rounds and any recurring-or-contradictory feedback, and a final approved version), treat the whole trail as the target rather than extracting just the final entry. Don't infer trail-ness from an untagged block of prose that merely contains multiple drafts or paragraphs, only labeled, tagged input counts as a trail; anything else is a single reply, even a long one. If input looks trail-like (multiple drafts present) but doesn't match this labeled structure, ask whether to treat it as a trail or a single reply rather than guessing. Quote the exact text being diagnosed before analyzing it, for a trail, that means quoting the specific round(s) that actually drive the diagnosis, not the whole document, don't work from a vague memory of it.

2. **Diagnose, don't assume.** Read the target text against the current Writing style section (`{{AGENT_CONFIG_DIR}}/AGENT.md`, "## Writing style"). Check it against each existing rule, most likely it already passes all of them, that's the actual problem this command exists to fix. Then read it fresh, as if a skeptical colleague were being handed it cold: what specifically reads as generated rather than written? Name the exact sentence or construction, not a vague "it feels off." If genuinely unsure, ask the user what bothered them about it rather than guessing.

   When the target is a trail, run both of the following checks, neither excuses skipping the other: (1) the same fresh-read test above, applied to the final approved version alone, and (2) a check of whether `apply-writing-rule` already tagged recurring or contradictory feedback across rounds when it assembled the trail, treat those tags as the primary signal rather than re-deriving them from scratch, and only scan the trail yourself if it arrives untagged. A final version that cleanly passes check (1) can still sit on top of a real gap surfaced by check (2), and a flagged pattern from check (2) can exist even when the final version looks fine in isolation, treat findings from either as equally valid input to step 3. If the final approved version itself still fails check (1) despite being signed off, treat that as its own, higher-priority finding, note explicitly that the user approved text which still reads as generated. Skip any round already tagged as technical or factual rather than stylistic, that's outside this command's scope regardless of input shape.

3. **Draft a surgical addition or change, not a rewrite.** The existing section is built as a dated, appendable list on purpose ("a dated sample of current tells, not exhaustive, when a new one shows up more than once, add it here with the date") so this command has somewhere to write. Prefer one new bullet under "Avoid these patterns" or "Structure" over restructuring what's already there, unless the diagnosis shows the existing structure itself is wrong. That's rare, and worth flagging explicitly if it happens.

   When the diagnosis came from a trail, ground the new bullet in the specific round(s) that recurred, quote one representative instance from the trail as the example even though the evidence spans several rounds, don't write a vaguer, unanchored bullet just because the source was a pattern rather than one sentence. A recurring failure usually still fits the new-bullet model above. A contradiction finding (feedback that reversed itself round to round) is different, that's evidence an existing rule, if any, is genuinely ambiguous, not that a new tell needs naming; route it to this step's "existing structure itself is wrong" branch instead of bolting on a new bullet that would paper over the ambiguity.

4. **Adversarial-review the draft before it touches disk.** Scale the review to the size of the change. A single new bullet gets a fast, solo pass checking it's testable, non-redundant with the existing rules, and doesn't contradict them. A structural change gets the full parallel hat treatment (Devil's Advocate, Gap Hunter, Systems Analyst at minimum, plus QA Reviewer for enforceability), the same way the section's last revision was done, see `{{AGENT_CONFIG_DIR}}/AGENT-review-log.md` for precedent and format. Either way, don't skip this step. Ad hoc fixes without review are how the section needed that last revision in the first place. A diagnosis derived from a trail always gets at least the structural-change level of review here, even if the resulting change is a single bullet, the diagnosis itself carries more inferential risk than a single-reply read, and that risk should be reviewed at the same rigor regardless of how small the resulting text change looks.

5. **Present the diagnosis and the reviewed draft together.** Quote the exact AGENT.md text that would change, and wait for explicit sign-off. Don't apply anything before the user replies. When the diagnosis is trail-derived, don't reproduce the whole trail here, quote the specific round(s) that drove it (per step 1) alongside the proposed AGENT.md text, and summarize in one line how many rounds or what pattern led here, so the user can verify the change without re-reading the full history.

6. **On sign-off**, edit `{{AGENT_CONFIG_DIR}}/AGENT.md` directly, and append a dated entry to `{{AGENT_CONFIG_DIR}}/AGENT-review-log.md` recording what was flagged, what changed, and why. That log is the section's own changelog, keep it current every time this command runs.

Reminder: this command only touches `{{AGENT_CONFIG_DIR}}/AGENT.md`'s Writing style section and its own review log, nothing else. If the flagged output's actual problem is technical, wrong information, not stylistic, say so and stop. That's not this command's job. When handed a trail, this reminder applies per-round: some rounds may be technical, others stylistic, only the stylistic ones are this command's concern (see step 2). Name which rounds were excluded as technical and why when presenting the diagnosis, so the user can check the exclusion themselves rather than take it on faith.
